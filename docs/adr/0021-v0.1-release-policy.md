## Context

v0.0.0 was tagged by Frank on 2026-09-23 after his qualified sign-off (R-017), with six of seven gates "met with limitations" printed by `scripts/v0_0_gate.py`. v0.1 has ten gates (V11–V20). The T08 specification finds that two of them carry a clause that is not met on existing evidence and cannot be met by bookkeeping:

- **V14 (b), one qualified PTC family.** T04 registered its criterion before running the comparison (T04 spec §8.1): the family qualifies iff the physical derivation holds *and* PTC's success set is not contained in damped Newton's on the registered comparison. The comparison gave 18 of 18 for both, PTC 1.9–8.8 times costlier. The plan anticipated this ("retain PTC as experimental and record the v0.1 gate as incomplete").
- **V13 (e), warm starts.** Blueprint §14.3 bullet 3 names "model initialization and warm starts"; §7.4 lists compatible warm starts as the second initialization source. T03's specification records that none exists in v0.1. The plan's V13 row omits the words; the blueprint clause counts (T08 spec FD1).

The plan requires that a failed requirement stays failed and that no clause leaves the denominator. It does not say whether a release may be tagged while one is failed. That is the decision this ADR frames and, for its general part, makes.

## Decision

### D1. The release candidate

A release candidate is a commit `C` on the release package's branch that satisfies T08 spec §8.1: the tree as it will be released with a pre-release version (`0.1.0rc1`); every RC-blocking item closed (spec §6.1); the envelope files passing their checks; the RC job of spec §8.2 completed at `C` with its records committed; the verdict document, the gate report and a `tested` manifest at `C`; nothing outward done. **Every gate is judged at `C`.** A package's earlier pass is evidence about its own commit and reaches `C` only through the RC job's re-run.

### D2. When a tag may be proposed

A tag `vX.Y.0` may be proposed to Frank iff, at `C`:

1. every gate of the release has a verdict (`PASS`, `FAIL` or `BLOCKED`) recorded in `docs/requirements.yaml` and in the verdict document, with evidence;
2. no gate is `BLOCKED`;
3. every `FAIL` is a clause listed in D3 **with Frank's acceptance recorded there**; and
4. the tag commit's `src/`, `schemas/`, `benchmarks/` trees and lock file equal `C`'s (only the version, the changelog, evidence and documents may differ), which `scripts/v0_1_gate.py` checks.

A released `FAIL` is printed `FAIL` in the gate report, the support matrix, the changelog and the manifest's limitations — never "met with limitations", never "waived". The tag itself is Frank's action.

### D3. The v0.1 clauses proposed to be carried as FAIL (each pending Frank)

| Clause | Why it is not met | Carried to | Recommended | Frank |
| --- | --- | --- | --- | --- |
| V14 (b) one PTC family qualified by §7.5 | T04 §8.3: PTC improves no tested basin; the criterion is not re-read after the result (R-118) | the first v0.2 package that registers a unit model with physical holdup, which owns T04 §8.4's preregistered PTC-R1; assigned at v0.2 planning, because the PyMRM reactor of M01 is an external steady model with no flowsheet holdup | carry as FAIL; PTC stays experimental and selectable by explicit policy only | F1 |
| V13 (e) compatible warm starts across runs | T03 spec: none in v0.1; K02's warm-start *cache* is a different mechanism (R-119) | M03 (sweeps are where warm starts pay), with S-G's GUESS roles | carry as FAIL | F2 |

If Frank answers "build" to either, that clause leaves this table and T08 builds it before the RC. If he answers "hold", no tag is proposed until the clause passes.

### D4. What the release notes must say

The `CHANGELOG.md` section for the release carries, in this order: what the release does; the gate table as `scripts/v0_1_gate.py` prints it, FAILs included; **what it is not** — not empirically validated (SYN-001 is synthetic), not a guarantee (R-017), not general beyond the support matrix, not a certificate of solution accuracy (ADR 0007 F3), PTC experimental, the agent evidence's scope (one model, MCP only); the known limitations by support-matrix id; the reproducibility promise in ADR 0007 F1's words (R0 structural identity, floats within the declared policy, bitwise agreement reported and never promised); and the review status of every package (`tested` or `reviewed`, with R-017's qualification where it applies).

### D5. What is not the release lane's to do

Tagging, publication (a GitHub release, repository visibility), PyPI (excluded by plan §2), mode-B artifacts (ADR 0006), purchases, rights requests and new agent campaigns (billed time) are Frank's. The release lane prepares the candidate and stops.

## Alternatives considered

- **Re-read V14 so that route (a) alone qualifies.** Rejected: it changes T04's registered criterion after the result; blueprint §15's risk row and plan §4.3 both say what to do when no basin improves.
- **Qualify PTC-R1 as a bare two-variable residual through T04's generic core** (about a day). Rejected as a V14 pass: no supported flowsheet can select that family, so it is not a v0.1 capability; T04 §8.4 itself assigned PTC-R1 to a package with a holdup reactor.
- **Read V13 by the plan's row alone** ("scaling and initialization"). Rejected: the plan summarises §14.3 and does not override it (CLAUDE.md: preserve v3.1).
- **Count K02's warm-start cache as V13's warm starts.** Rejected: it is the §6.4 property-level hint mechanism, not a §7.4 initialization source.
- **A "PASS with waiver" status.** Rejected: a reworded FAIL; the ledger's vocabulary has no such word and should not gain one.
- **Tag on package-level passes without an RC re-run.** Rejected: T07 changed code after T06's campaigns; plan §6.5 requires the full registered gate after a solver-policy change and names a release-candidate job.
- **Hold the tag until every clause passes.** Not rejected: it is F1/F2's option (iii), Frank's to choose.

## Consequences

- T08 builds `scripts/v0_1_gate.py` (T08.A50), the RC job (spec §8.2), the support matrix and the changelog draft.
- The v0.2 plan must name an owner for V14 (b) and for V13 (e) if D3 is accepted; until a package qualifies a family under R-118's criterion, PTC stays experimental in every release.
- A later release reuses D1, D2 and D4 unchanged; D3 is per release.

## Migration

None. No schema, interface, stored hash or registered value changes.

## Proposed revision 2 (2026-10-01, T08 release spec Amendment R3 4) — D2.4's tree check, as paths

**Status:** Proposed, design lane; register R-139. D1, D2.1–D2.3, D3, D4 and D5 are unchanged.

**D2.4, revised.** The tag commit's distribution sources — `src/`, `schemas/`, `benchmarks/`, `requirements.lock`, `pyproject.toml`, `MANIFEST.in`, `README.md`, `LICENSE`, `NOTICE` — equal `C`'s byte for byte, except one occurrence of the version value in each of `pyproject.toml` and `src/process_runtime/__init__.py` (`0.1.0rc1` → the tag's). Every other path may differ (the changelog, `docs/`, `evidence/`, `tests/`, including the test fixtures that carry the version). `scripts/v0_1_gate.py` checks it (T08.A50). A change to a checked path after `C` makes a new release candidate, not a tag.

**Why.** The original "`src/`, `schemas/`, `benchmarks/` trees and lock file … (only the version, the changelog, evidence and documents may differ)" left out inputs that become bytes of the released sdist and wheel: the dependency pins (`pyproject.toml`), the packaging rule (`MANIFEST.in`), the long description (`README.md`, which also carries T08.A31's LGPL statement) and the licence files (`LICENSE`, `NOTICE`; T08.A31). A change to any of them after `C` would reach the released artifacts untested by T08.A31 and A43.

**Rejected.** The original path set; a byte comparison of artifacts rebuilt at the tag (needs a version-normalizing diff of file names and METADATA, for no more coverage than the source list).
