## 2. Amendment R7 1: CONFIRMED as a transcription

- **It is faithful to G6.** G6 asked for "a tracked location outside the checked paths, for example
  `evidence/T08/<C>/rc/` un-ignored for the small texts" (`docs/reviews/T08-verdicts.md:473-479`). R7 1 adopts
  exactly that. ADR 0021 revision 2 (`docs/adr/0021-v0.1-release-policy.md:117`) lists `evidence/` among the
  paths that may differ between `C` and the tag, so D2.4 holds.
- **It changes nothing the verdicts relied on.**
  - The per-step table of `docs/t08-rc-record.md` is byte-unchanged since `51cd5ff`, which is an ancestor of the
    verdict commit `f22f3cf`. Commit `5d90e6b` only adds a dated note.
  - All 42 committed files hash to their table entries, and the test asserts that the 44 cited hashes and the 44
    listed hashes are the same set.
  - No record was regenerated.
- **F1 (should-fix; needs a decision).** The 1 MB size limit is a build-lane parameter that §8.1 and G6 did not set.
  - **Effect.** It leaves G6's retention problem open for exactly two files: `ensemble/rc-ref-x86-64.json` and
    `ci/rc-ensemble-ubuntu-24.04-arm/rc-ci-aarch64.json`, 2.4 MB each.
  - **Why it matters.** These are the per-start records behind V20 (d)'s S = 434 on both classes. The committed
    `rc-ref-x86-64.report.txt` carries per-case counts only. These two files still exist only on `ref-x86-64`
    (git-ignored) and as CI artifacts with finite retention.
  - **Scenario.** The CI artifacts expire and this host is lost. S = 434 can then no longer be recomputed from the
    record, only re-run.
  - **Fix, recorded as a new decision appended to R7 1.** I recommend committing both files under
    `evidence/T08/<C>/rc/`, gzip-compressed if size matters, with `records.json` keeping the sha256 of the
    uncompressed bytes. They are text, not binaries, so the large-artifact rule does not forbid it. The alternative
    is a durable store named by hash, such as the private archive repository or a release asset.
- **N3 (note).** The verdict says "43 of 43 sha256 equal the record" (`T08-verdicts.md:68`). The RC record's table,
  which predates the verdict, cites 44 (`tests/test_t08_rc_records.py:61` asserts 44).
  - **Effect.** Integrity is not in doubt: the test now checks all 44.
  - **Gap.** Which record the verdict did not recount is unexplained.
  - **Fix.** Add one erratum line to the RC record note, or a verdict-ledger note, naming the 44th record.

## 4. Q1, T08.B24 (`5323046`): CONFIRMED

- **The test discharges the row.** Row B24 (`docs/derivations/T08-build-first-spec.md:439`) has three exact clauses,
  and `tests/test_t08_b24_ptc_job.py` asserts each one:
  - the job ends typed: a status in `TERMINAL_STATUSES`;
  - `branch_provenance[0].core == "ptc"`, read from the certificate or failure bundle the job wrote;
  - `T08-ptc-v1` is in `get_project.solve_policies`.

  It uses the §A2 revision (`benchmarks/t08/ptc_r1/revision.json`) through `LocalApplication.submit_job`.
- **"Recorded, not asserted" is the row's own design.** It is not the build lane's softening: §A4.7
  (`T08-build-first-spec.md:266`) says "the outcome is recorded and not asserted".
- **`unsupported` would have been the wrong call.** The capability exists and is exercised, and declaring it
  unsupported would have misreported it.
- **The test's timing changes nothing.** Writing it after the verdicts cannot move V14 (b), which is FAIL on (b1)'s
  saddle clause. The V14 (b) verdict says so itself: "B24, B25 and B20's outstanding clause cannot change it"
  (`T08-verdict-V14b.md:41`). The criteria were fixed before the test, so this is no re-reading.
- **The crash path is caught.** A terminal job with no run result passes the second assertion
  (`result is None or result.outcome`). It is caught by the third, which needs a written bundle.
- **N6 (note).** "Recorded" is met only in prose: the docstring and the commit message say "CONVERGED, VERIFIED,
  21 PTC iterations". The manifest's B24 entry records only "3 passed". A later build whose outcome changes would
  still pass while the docstring went stale. The docstring is dated to `C`, so it is a historical statement and is
  acceptable for v0.1. Fix, for v0.2 hygiene: have the test emit its outcome, certificate status and PTC iteration
  count into the manifest's B24 value.

## 5. Q2, A21 harvest (`1305f87`): CONFIRMED; no denominator was narrowed

- **The exclusion restores the denominator judged at `C`.** At `C` the tree holds 18 manifests and none under
  `evidence/T08/` (`git ls-tree -r C evidence`). The T08 manifest is necessarily written after `C`. A21 at `C`
  therefore judged exactly §5.7's "18 manifests"; the exclusion restores that set and does not shrink it.
- **This was the design lane's intent from the start.** `HARVEST_PACKAGES` (`docs/derivations/scripts/t08_reference.py:541`,
  P00–T07) was written by the design lane with the spec itself in `2273f3e` (2026-09-29), before any T08 manifest
  existed. Its count check `A21.harvest_size_as_quoted` pins 18 manifests with 87 + 145 limitations.
- **The denominator is pinned in the test.** `tests/test_t08_w2_support_envelope.py` (`(len(manifests),
  len(limitations)) == (18, 232)`, `len(envelope["harvest"]) == len(items)`) pins it, so the exclusion cannot
  silently drop more.
- **The exclusion fails loudly on new manifests.** It is a prefix exclusion, not an include list, so any other
  package's manifest is still harvested and fails A21 if it is unclassified.
- **The literal reading is unsatisfiable.** Classifying T08's own manifest would mean editing
  `benchmarks/t08/support_envelope.yaml` after `C`. That is the same D2.4 circularity as G6.
- **F2 (should-fix; erratum).** §9's A21 row (`T08-release-spec.md:472`) still says "over every
  `evidence/**/manifest.json`", which the code no longer does. Fix: a design-lane erratum amending the row to
  "over P00–T07's manifests (§5.7; `HARVEST_PACKAGES`); T08's own manifest, written after `C`, is the next harvest's".
- **F3 (should-fix; v0.2 hand-on).** Nothing classifies T08's own manifest items: 58 limitations plus the non-pass
  A70 and B23.
  - **What I measured.** 16 of the 58 carry no `Lnn`/`Unn` id. Some are process notes. Others read as user-facing:
    the V19 feasibility limits, `library-only` paths, and the two uncommitted ensemble files.
  - **What I did not check.** Whether each of those is already an envelope row.
  - **Fix.** Record in v0.2's state and backlog that `evidence/T08/67c66d9…/manifest.json` is an input to the next
    harvest, which is the v0.2 envelope's, so nothing T08 handed on is lost.
