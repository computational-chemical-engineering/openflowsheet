## 2. Ruling 1: W5-8, the `sha256` partition

**Facts, measured at `a6a760bf`.**

- `scripts/t08_numerical_policy.py --check` fails with "(d) unclassified sha256 names: ['descriptor_sha256',
  'registry_sha256', 'self_sha256']". F1-WO4a's three `$defs` of `application-results.schema.json`
  (`capability_descriptor`, `capability_page`, `admission_report`) declare those names as properties. The schema is in
  v2's domain (no addendum lists it), and only F1's addendum classifies the names, for F1's own two schemas. The values
  already `$ref` F1's schemas; only the property names sit in `application-results`.
- The comparator reads only v2's `float_digests` and suffix (`run/compare.py:458-479`). A `sha256` name it does not list
  as a float digest is compared exactly. All three names are exact (their preimages are declared data and file bytes).
  So the defect is in the partition's bookkeeping. No comparison is wrong.
- **The engineer's premise about (b) is false for a verbatim move.** I moved the three `$defs`, unchanged, into
  `registry-snapshot.schema.json` and left in `application-results` a `$def` of each name that is exactly `{"$ref":
  "https://github.com/frankp/process-runtime/schemas/registry-snapshot.schema.json#/$defs/<name>"}`. This was done in
  memory, in the process that computes them. The served digest stayed D_9 = `e2c44b6b9c2a7f5689ed4f2fd96b6e9804d1a63e60a5c620d29b5b5d594bcebb`.
  The R4-G3 digests stayed `list_capabilities` `d786a16f050783886196dbf3a12ccfd40c19fa59b934a3c5480dc925144bbe29` and
  `check_admission` `d04b98395b96b33e94de4dd48678bd31c24ddb1cf7c42b1ca9455e27f25da43f`. Controls: a changed
  `maxLength` in a moved body moved both R4-G3 digests, and a changed description moved D_9. So both measures read the
  moved bodies. Both are taken over the `$ref`-resolved schema (`bindings/mcp.py` `self_contained`;
  `test_t07_w5e_application_results.py` `resolved_response`). A bare `$ref` resolves to its target unchanged.
- On a copy of `schemas/` with that move, `--check` passes:
  "benchmarks/t08/numerical_policy_v2.yaml equals the regenerated bytes (sha256 6b449911f4e692051b08372fefaf0e205e9b2d746362e4fba2c4a9f6e19d707c)",
  v2's bytes unchanged (R-1005's watch value). On a full copy of the worktree with the move, 534 of 536 selected tests
  passed. The selection was: the four red tests (and the files of two of them), the six `test_f1_*.py`, R4-G3, the
  surface digest and chain, and five other readers of `application-results`. One failure was
  `scripts/t07_schema_fixtures.py:292`, which reads `schema["$defs"][name]["required"]` and needs to follow the
  pointer. With that fixed, the fixture test passes and no fixture changes. The other failure needs `.git`, which the
  copy lacks, and it passes in the worktree.

**Ruling: option (b), specified as a verbatim relocation** (WO6 part A; ADR 0060 D11 "Where the shapes live"; R-1032).
F1's three result shapes become `$defs` of `registry-snapshot.schema.json`, and `application-results.schema.json` keeps
a bare-`$ref` `$def` of each name. No `sha256` name enters v2's domain. This is the structure E01 (its study and
optimization-report schemas reach `assessment_link` by `$ref`) and OPT (`report_revision`) already chose for the same
case, and their addenda say so in those words. ADR 0025, its A1 audit, v2's data and every addendum's data stay as they
are. D_9, `SNAPSHOT_F1` and R-1030 do not move.

**Rejected.**
- **(a) Extend "a reused name keeps its class" to v2-scope schemas.** It is coherent: classes belong to names, and an
  addendum can only add exact names, which is the comparator's default. But it rewrites the audit of an Accepted ADR's
  assertion (A1(d)), so v2's data would no longer list every name its own schemas declare. That needs an ADR 0025
  amendment for a case two packages solved without one. Its stated advantage (no D_9 move) is shared by (b).
- **(c) A v3 policy.** A new policy id for a bookkeeping matter. Every record is compared under the policy it names
  (R-147), so this would fork comparison semantics for nothing.
- **(d) List `application-results.schema.json` in F1's addendum** (the only one-line registration). It fails A1(d):
  "classified but undeclared: ['content_sha256']", because `content_sha256` is declared only in `application-results`
  in v2's domain. It would also hand ADR 0019's shared contract schema to one package's table. No later addendum may
  list a schema an earlier one claims, so every later `sha256` name in `application-results` would have to enter F1's
  table.

## 3. Ruling 2: F-4, the built-in `lca` contributor and `dependency_missing`

**Facts, measured at `a6a760bf` in the project venv.** `bw2data` and `bw2calc` are not installed.
`openflowsheet.assessment.lca.section.LcaContributor` imports without them (no Brightway module is loaded), and E01's
`program._REGISTERED` holds `lca`. Yet `default_registry().factory("functional_contributor", "lca")` raises
`FactoryRefusedError(dependency_missing{id: lca, extra: lca})`. The contributor evaluates frozen unit-score tables.
Brightway serves only the offline adapter `assessment/lca/brightway.py`, which imports it lazily and refuses
`UNSUPPORTED(LCA_ENGINE_UNAVAILABLE)` by itself (ADR 0052 D7; `pyproject.toml`'s comment on the `lca` extra: "Never
imported by a solve, an optimization or a replay").

**Ruling: not intended.** The registry would refuse, as missing a dependency, a contributor E01 runs. The defect is
W3-8's `pip_extra: lca` on the descriptor, not SF-3's presence check. D2's old wording ("the extra that installs the
implementation's optional dependencies") allowed both readings. D2 now says (erratum F-4): `pip_extra` is the extra
whose requirements the implementation needs in order to be constructed and run, and it is null when the implementation
runs without any extra. A dependency that only a separate optional path needs, where that path refuses by itself, is
not named. So the built-in `lca` contributor's `pip_extra` is null, and `coolprop-heos-v1`'s stays `coolprop`: its
provider cannot be constructed without CoolProp, and SF-3's test with CoolProp masked keeps its refusal. Expected
consequence (WO6 part B): only the `lca` descriptor's `descriptor_sha256` moves
(`faf8ccb8a8fc55478db28821c62e70b3e786645751ba677c2d3d81fd1e053754` to
`18fab1d2d5b84f039289345fcaef516cf3fe724e980f819ef6eec0b2da333833`). `registry_sha256` moves from
`f47226241272060a7c49d9780311b6f3a93204f1bb9818a295eefa38245f5c2a` to
`f251447d06a6e8267cabc655a46dae1ae556827b295538434f7a14ba2dde7058`. These values come from building the registry with
the committed tables and that one field set to null, and from the generator's `--write` on a copy. They are regression
expectations that check part B changes nothing else, not an independent validation.

## 4. Ruling 3: F-5, D1's "core" for `record_type`, `correlation_form` and `data_source`

**Ruling: yes, an erratum.** D2 validates a payload "by the kind's payload schema", and those three kinds have none in
F1 (`PAYLOAD_DEFS` holds only `message_entries`; ADR 0061's work order installs the others). A `core` label on a
descriptor that nothing has validated would claim a frozen contract that nothing checks. SF-4's build is right, and D1
now says so: "**A core kind before its payload schema**" (ADR 0060 D1, erratum F-5). Per descriptor, core holds only
once the kind's payload schema is installed. Until then a non-built-in descriptor of the kind is `preview` and carries
`preview_kind`. It becomes core when the schema lands, with no edit, and a payload the new schema refuses then
quarantines its package. D12's preview list gains this case. One claim needs executable form, so that ADR 0061's work
order cannot break it silently: a **built-in** of such a kind is never registered without its schema. The generator
refuses such a built-in (WO6 part D). SF-4 left the built-in branch `core` unconditionally. No built-in of those kinds
exists today, so the refusal holds trivially now and guards the next table.

## 8. What this document does not establish

- **It does not validate the predicted digests.** `f251447d…`, `18fab1d2…` and `3e69d0c7…` were computed with the code
