## 1. Scope, authority, and what is explicitly out of scope

**What P02 measures.** Two harnesses — one on CasADi 3.8.0, one on Pyomo 6.10.1 with PyNumero's ASL interface — each expose the *same* SYN-001 subsystem (§2) through the frozen `CompiledProblem` boundary (`residual(x, context)`, `jacobian(x, context)`, `reconstruct(x, context)`), with the SYN-001 K-value vector and a second, deliberately sparse enthalpy block entering as **opaque callbacks with declared first-derivative sparsity**. At registered states (§5) the harness output is judged, in the repository environment, against closed-form residuals and Jacobian entries (§6), a linear solve with an explicitly configured SuperLU (§9), and a separate second-order probe (§8). The judge is one code path for both backends; the harnesses only produce artifacts.

**Design invariants.**

1. Expected values come from the closed forms of SYN-001 §3 and §2 below, evaluated at the registered double-precision state vectors, never from either backend (CLAUDE.md, brief §7). The generator script and YAML are the executable provenance.
2. No assertion is satisfiable by an accidental zero. Every structural nonzero is asserted nonzero at at least three states; the two states where subsets vanish (S3, S4) are registered *because* they vanish there, and the assertion at those states is "present in the pattern and exactly zero", paired with "nonzero elsewhere".
3. Both harnesses are measured on identical ground: the same variables, equations, orderings, parameters, states, directions, counters, and one judge. Where the routes cannot produce the same raw matrix (they cannot; §4.3), the reduction to common ground is defined by name, and the raw structure is recorded too.
4. Unsupported is a result, not a pass. A missing capability is declared in metadata and returns an explicit unsupported result; a dense or finite-difference fallback is detected (§11.2) and is a failure of the sparse-composition criterion.
5. `scripts/check.sh` passes in the repository environment with no backend installed. Backend code lives in `spikes/p02/` (not type-checked, not collected by the repository pytest); the judge lives in `benchmarks/p02/` and `tests/` (type-checked, collected) and skips a backend with a stated reason when its artifacts are absent.

**Out of scope.** Choosing the backend (P03). Solving the nonlinear system, globalization, scaling policy, phase-attempt control (K03, ADR 0004/0005): P02 evaluates residuals and Jacobians at given states and performs one linear solve. Canonical hashing (ADR 0002): P02 uses a local, documented state-hash convention (§10.4) that K01 replaces. The `PropertyProvider` protocol and `PropertyCapabilities` schema (K01/K02): the P02 callbacks are spike objects, not providers. Any change to the frozen interfaces or ADR 0001 — none is needed; one finding about schema timing is recorded in §12.

## 2. The compiled subsystem

### 2.1 Choice and rationale

The compiled subsystem is a **single isothermal–isobaric flash of a fixed feed with specified temperature and pressure and a computed duty**, written in component flows (ADR 0001 D2/D3: no division by total flow, K-form equilibrium so ln 0 is never evaluated), with **lifted intermediates** so that the property callbacks enter through explicit variables and defining equations. The recycle tear is **not** included: SYN-001 §5.1 proves the loop reduces to this flash, so the tear adds only linear rows and would add nothing to the callback composition test; it belongs to K02/K03.

Two forms are defined. The **L-form** (lifted) is the matched ground for both backends. The **I-form** (inlined) substitutes the callbacks directly into the equations and is the form in which CasADi applies the chain rule across the callback boundary; the Pyomo grey-box route cannot produce it (§4.3), so it is a CasADi-only capability record, cross-checked from both backends' L-form matrices by exact Schur elimination at the lifted-consistent states S1–S4 (§6, A14).

### 2.2 Fixed parameters

| Symbol | Meaning | Unit | Where it comes from |
| --- | --- | --- | --- |
| `f = (f_A, f_B, f_C)` | feed component molar flows | mol/s | state table §5 |
| `H_feed` | feed enthalpy flow | W | state table §5 (0 exactly for the 300 K liquid feed; nonzero at S5/S6 by design) |
| `T_spec`, `P_spec` | specifications | K, Pa | state table §5 |
| SYN-001 constants | R = 8.31446261815324 J/(mol K), T_r = 300 K, P_r = 100 000 Pa, c_p = 100 J/(mol K), T_b = (320, 360, 400) K, L = (25 000, 30 000, 35 000) J/mol, v = (1e-4, 1e-4, 1e-4) m³/mol | — | plan §3.1 |

Domain: 280 K ≤ T ≤ 440 K, 50 000 Pa ≤ P ≤ 200 000 Pa, closed. **Both** callback blocks — K and H, in both their value and their Jacobian methods, on both routes — check `(T, P)` against this domain on every call and raise a typed domain error naming the offending value when it is violated; the boundary reports that as `invalid_trial_state` (A17). The guard is not optional and may not be dropped to make a finite-difference stencil evaluable: every registered stencil (A04, A07, A15) is chosen to stay inside the closed domain, and the generator asserts this (`stencil_domain_checks`), so a harness that needs to remove a guard has found a specification error to report, not a nuisance to bypass. A property block that silently extrapolates outside its declared validity is exactly what this fixture exists to catch, and K02's provider carries the same obligation.

### 2.3 Closed forms (SYN-001 §2–§3)

    lnK_i(T,P)   = ln(P_r/P) + (L_i/R)(1/T_b,i − 1/T) + v_i (P − P_r)/(R T)
    ∂lnK_i/∂T    = [L_i − v_i (P − P_r)] / (R T²)
    ∂lnK_i/∂P    = −1/P + v_i/(R T)
    ∂²lnK_i/∂T²  = −2 [L_i − v_i (P − P_r)] / (R T³)
    ∂²lnK_i/∂T∂P = −v_i/(R T²)
    ∂²lnK_i/∂P²  = 1/P²
    h_i^L(T,P)   = c_p (T − T_r) + v_i (P − P_r)          (liquid molar enthalpy, J/mol)
    h_i^V(T)     = c_p (T − T_r) + L_i                    (vapor molar enthalpy; independent of P)

Note for implementers: ∂lnK_i/∂P is identical for all three components at *every* (T, P) because the v_i are equal; the P column never distinguishes components. ∂lnK_i/∂T differs by component at every state (the L_i differ). K_B(360 K, P_r) = 1 exactly and h_i^L(300 K, P_r) = 0 exactly; no evaluation state relies on a value at those coincidences except where §5 says so.

The `tspec`/`pspec` rows make the system square with T and P free, so the callback derivative columns are exercised by the Jacobian and by the linear solve at a perturbed state (§9).

Row and column scales are the tables above. Measured κ₂(J_s) is 38–417 at the registered states versus 1.5e9–4.8e10 unscaled (§9), which is the reason the linear-solve evidence is on the scaled system.

### 2.6 I-form (CasADi-only): 11 variables, 11 equations, 43 nonzeros

Variables: `v_A, v_B, v_C, l_A, l_B, l_C, V, L, T, P, Q` (same scales). Equations: `bal_i, Vdef, Ldef, eq_i, energy, tspec, pspec` with `eq_i = v_i L − exp(lnK_i^cb(T,P)) l_i V` and `energy = Σ v_i h_i^V(T) + Σ H_i^cb(l,T,P) − H_feed − Q`. Jacobian entries that differ from the L-form:

| Row | Column | Entry | Origin |
| --- | --- | --- | --- |
| `eq_i` | `T` | `−K_i l_i V ∂lnK_i/∂T` | chain rule through block K |

## 3. The two callback blocks and their declared sparsities

Both blocks are **opaque at first order**: value and Jacobian are computed by Python code that the backend cannot differentiate. In CasADi this means the `Callback.get_jacobian` method returns *another* `Callback` (not a symbolic `Function`); in PyNumero it is the `ExternalGreyBoxModel` contract by construction. This is what a compiled property provider looks like from the backend's side (blueprint §6.4), and it is the condition under which the second-order probe (§8) is meaningful. A symbolic-Jacobian CasADi variant is allowed only as the labeled supplementary record H5.

### 3.1 Block K — the SYN-001 K-value vector

- Inputs: `θ = (T, P)`, 2 entries. Outputs: `(lnK_A, lnK_B, lnK_C)`, 3 entries, in component order A, B, C.
- Value: the closed form of §2.3. Jacobian (3 × 2), **declared dense**: `∂lnK_i/∂T`, `∂lnK_i/∂P` from §2.3. There are no structural zeros in this block; its role is exact values, component ordering, and the chain rule.
- Output is ln K, not K, so that the assembled `kdef_i` rows carry the reference derivatives `−∂lnK_i/∂T`, `−∂lnK_i/∂P` verbatim (20-digit reference at S1: `benchmarks/syn001/reference_values.yaml` key `lnK_derivatives_at_360K_P_r`) and the exponential is left to the backend's AD in `eq_i` (L-form) or in the chain (I-form).
- Domain enforcement is inside the block: T or P outside the closed domain raises a typed error naming the value.

### 3.2 Block H — liquid component enthalpy flows, intentionally restricted

- Inputs: `ζ = (l_A, l_B, l_C, T, P)`, 5 entries. Outputs: `(H_A, H_B, H_C)` with `H_i = l_i · h_i^L(T, P)`, W.
- Jacobian (3 × 5), **declared sparse with exactly 9 nonzeros**: `(H_i, l_i) = h_i^L(T,P)`, `(H_i, T) = l_i c_p`, `(H_i, P) = l_i v_i`. The six off-diagonal flow entries `(H_i, l_j≠i)` are structural zeros: ideal mixing makes each component's enthalpy flow independent of the other components' flows. A backend (or harness) that declares or stores 15 entries has densified the block (A05).
- The block is bilinear, so a fourth-order central difference is exact up to roundoff (used by A07).
- Domain guard identical to block K's (§2.2): the value and the Jacobian methods both raise the typed domain error outside the closed domain.
- The restriction is *visible in the assembled L-form* because each output feeds its own `hdef_i` row; `(hdef_i, l_j≠i)` must be absent from the assembled pattern (A08).

### 3.3 Counters (identical in both harnesses)

Each block object carries two integer counters incremented inside its Python value method and its Python Jacobian method respectively (`value_calls`, `jacobian_calls`). The harness records them before and after every `residual()`/`jacobian()` call and over the compile phase. A call is one invocation of the Python method, whatever the backend's batch size. Nothing else counts.

### 4.2 Structural zeros versus numerically vanishing entries

The pattern is a property of the *formulation* and is the same at every state. At two registered states, subsets of the structural nonzeros are numerically zero because a total flow is exactly zero; they must remain stored in the pattern with value exactly `0.0`:

| State | Numerically-zero structural nonzeros (count) |
| --- | --- |
| S3 (LIQUID, V = 0, v = 0) | `(eq_i,l_i)`, `(eq_i,L)`, `(eq_i,lnK_i)` for i = A,B,C; `(energy,T)` — **10** |
| S4 (VAPOR, L = 0, l = 0) | `(eq_i,v_i)`, `(eq_i,V)`, `(eq_i,lnK_i)` for i = A,B,C; `(hdef_i,T)`, `(hdef_i,P)` for i = A,B,C — **15** |

Every one of these entries is nonzero at S1, S2 and S5 with |entry| ≥ 1.58e-5 in unscaled units (minimum is `(hdef_A,P)` at S2), far above the assertion floor. At S1, S2, S5 and S6 all 60 entries are nonzero (minimum 4.97e-6, `(kdef_A,P)` at S6). The I-form has its own, smaller floor: over S1, S2, S5, S6 the minimum of the entries that vanish at S3/S4 is 3.35e-6 (`(eq_C,P)` at S1 = −K_C l_C V ∂lnK_C/∂P, small because ∂lnK/∂P is of order 1e-5 in this fixture), so A13 uses a 1e-6 floor, not A11's 1e-5. No structural zero is asserted at a state where a term merely vanishes; the structural-zero assertion (A08) is on the pattern, the vanishing assertion (A11) is on values, and they are separate.

### 4.3 What "the same pattern" means when the routes assemble different matrices

Measured facts (coordinator, 2026-09-10, installed casadi 3.8.0 and pyomo 6.10.1 with the ASL interface): CasADi's `jacobian(r, x)` eliminates callback outputs and returns the chain-ruled matrix. The PyNumero grey-box route carries callback outputs as explicit NLP variables plus output constraints `output − f(input) = 0`. With `set_external_model(block, inputs=[existing Vars], outputs=[existing Vars])` the block attaches to the model's own variables: a toy with inputs (T, P), outputs (lnK_A, lnK_B, lnK_C) and two spec rows gives primals `['P','T','lnK_A','lnK_B','lnK_C']`, constraints `['tspec','pspec','kb.output_constraints[lnK_A]', …]`, 5 × 5, nnz 9 — no input copies, no link rows. With the block's own `inputs`/`outputs` plus link constraints the same toy is 10 × 10, nnz 19. So the grey-box output-constraint rows are the `kdef_i`/`hdef_i` defining rows of §2.4 **up to sign**: PyNumero writes an output constraint as `f(inputs) − output`, the negative of §2.4's `output − f(inputs)` (measured natively: `(kb.output_constraints[lnK_A], T) = +∂lnK_A/∂T`, `(…, lnK_A) = −1`, `(hb.output_constraints[H_A], l_A) = +h_A^L`, where §2.5 requires `−∂lnK_A/∂T`, `+1`, `−h_A^L`). The Pyomo L-form is therefore natively the 17 × 17 matrix with those six rows negated. (Constraint order is still not declaration order; A01 stays name-keyed.)

The comparison is defined at three levels:

1. **Block level.** The callback's own Jacobian, as reported by the backend's sparsity accessor (CasADi: `get_jacobian` Function `sparsity_out(0)` and its evaluation; PyNumero: the COO from `evaluate_jacobian_outputs()`), is compared with the declared pattern and closed-form values (A02, A05, A06).
2. **System level, matched (L-form).** Both backends deliver the 17 × 17 L-form in the §2.4 ordering, natively and with no reduction step. CasADi builds it with lifted `lnK_i`, `hL_i` symbols and `kdef`/`hdef` rows (the callbacks are called on `(T,P)` and `(l,T,P)` inside those rows only). Pyomo builds it with `set_external_model(..., inputs=[m.T, m.P], outputs=[m.lnK_A, …])` so that `kb.output_constraints[lnK_i]` is `−kdef_i` and `hb.output_constraints[H_i]` is `−hdef_i`. The harness maps names to §2.4 ids (A01) and applies a **declared row-sign adapter** to reach §2.4: one module constant `OUTPUT_ROW_SIGN = −1.0` multiplies exactly those six rows, residual and Jacobian together (an exact row scaling, so residual and Jacobian still describe the same function; no other row is touched), and `raw_structure.json` records the native orientation `f(inputs) − output`, the specification's orientation, the six affected row ids and the constant's name. The block-level exports (A02, A05, A06) stay unsigned: they read the block as §3 declares it. This is a convention adapter, not a fudge, and it is falsifiable: if PyNumero's native orientation were §2.4's, the same negation would flip twelve entries and A10 would fail. It keeps one canonical matrix for the cross-backend assertion A21 rather than teaching the judge two conventions. Plain equality constraints are *not* an alternative: they would make the block Jacobian 3 × 8 with 12 entries instead of the declared 3 × 5 with 9 and break A02/A05/A06. **Fallback only:** if the keyword form is rejected on the full 17-variable model, the harness uses the block's own `inputs`/`outputs` with link constraints and performs a *named elimination of link rows* (for each `model_var − copy = 0`: add the copy's column into the model variable's column, delete the link row and the copy column — exact, since the link Jacobian is `+1/−1`), exports raw and reduced, and records the fallback under A24. The link-form run is not a required variant.
3. **System level, inlined (I-form).** CasADi natively (11 × 11, 43 nonzeros). Both backends indirectly by exact Schur elimination of the lifted variables from their L-form matrices (A14). Pyomo cannot assemble the I-form natively; that is recorded as a capability fact, not a failure.

| H5 | supplementary, CasADi only | H2 and H4 repeated with `get_jacobian` returning a *symbolic* `Function` of the closed-form derivatives instead of an opaque Callback | same values | records that second order becomes available only when the provider ships differentiable derivative code — a capability fact for K01, labeled supplementary and never mixed with H1–H4. Measured during implementation (casadi 3.8.0): with opaque Jacobian Callbacks every second-order request raises `MX::ad_forward for node of type Call` (→ `absent`); with a symbolic block Jacobian all eight probed entries return and match the closed forms above (1.2889269873405998e-4, 9.28027430885232e-11, −1e-10, −100, −1e-4, −0.08968397695354713, −4.7122731764580447e-4). |

Mechanism. CasADi: `hessian(φ, x)` (or `jacobian(jtimes(r, x, e_k), x)`), evaluated at S1. PyNumero: `nlp.set_duals(λ)`, `nlp.set_primals(x)`, `nlp.evaluate_hessian_lag()`.

**Recording rule (A22).** Each entry is exactly one of:

- `exact` — a number is returned and `|H − E| ≤ 1e-10 |E| + 1e-14 s_r/(s_c s_c')` (floor as in A10, two derivative factors);
- `absent` — the backend raised or returned a declared-unsupported result for the **whole** request, `metadata.capabilities.hessian == "absent"`, and the exception type and message are recorded verbatim;
- `fabricated` — a number is returned that is not `exact` (this includes a zero where `E ≠ 0`, and a partial matrix in which H1 is right and H2 is zero).

The expected honest outcome (plan: "neither without additional declarations") is: H1 `exact` or `absent` in both (CasADi computes the algebraic Hessian if the graph permits; PyNumero's grey-box Hessian path raises for the whole NLP); H2, H3, H4 `absent` in both. A backend that returns H1 and zeros for H2 is `fabricated` and fails A22 — this is precisely the "missing second-order capability fabricated rather than reported absent" trap. The probe never feeds any first-order assertion.

## 9. The SuperLU common solve and the linear-residual evidence (D03)

**Where.** In the repository environment (scipy 1.15.3, pinned), by `benchmarks/p02/linear_solve.py`, on the L-form matrices **exported by each backend** at S1–S6 and S1p. The solver, its configuration, and the code path are therefore identical for both backends; only the matrix source differs. (The backend venvs' own scipy versions are never used for this evidence.)

**Configuration (explicit, recorded verbatim in the manifest).** `scipy.sparse.linalg.splu(J_s, permc_spec="COLAMD", diag_pivot_thresh=1.0, options={"Equil": False, "SymmetricMode": False})` where `J_s = D_r⁻¹ J D_c` is formed by the judge from the exported unscaled CSC and the §2.4 scales. Equilibration is off so that the registered scales are the only scaling in play; the `options` keys are verified to be accepted by scipy 1.15.3 (this specification's generator ran them).

**What is solved and asserted (A23).**

| Sub-item | Solve | Expected | Tolerance and floor |
| --- | --- | --- | --- |
| A23.1 | Newton step at S1p: `J_s Δ_s = −D_r⁻¹ r(x_pert)` with `r`, `J` from the backend at S1p | scaled linear residual `‖J_s Δ_s − b_s‖_∞ / (‖J_s‖_max ‖Δ_s‖_∞ + ‖b_s‖_∞)` | ≤ 1e-14; measured 3.8e-17 with κ₂(J_s) = 175.5; floor n ε ≈ 2e-15 |

## 11. Pass/fail verdict rules, and what P02 does not establish

### 11.1 Per-backend composition verdict

- **PASS-composition:** every mandatory assertion for that backend (A00–A12, A14–A20, A22, A23; plus A13 for CasADi, A24 for Pyomo) is `pass` at every applicable state, and every M-series measurement is recorded per protocol.
- **FAIL-composition:** any mandatory assertion `fail`. A failure stays a failure; states are not removed and tolerances are not widened. If the specification is found wrong (as in the P01 FD case), the correction is a Fable-authored amendment to this document with the measured floor, not a harness-side change.
- **BLOCKED-<reason>:** a mandatory assertion is `unsupported` because the route cannot execute it (for example the ASL library cannot be built, or CasADi refuses the Callback embedding). Never reported as PASS. The reason and the evidence are in the manifest `limitations`.
- The capability records (A16 for Pyomo, A13 for Pyomo, H-series) do not enter the composition verdict; they enter P03's decision matrix as facts.

### 11.2 Dense fallback and finite-difference fallback, operationally

A backend result is a **dense fallback** if any of: (a) A08 finds entries outside the expected pattern; (b) any block's stored Jacobian has nnz equal to `n_out × n_in` while the declared pattern is smaller (A05); (c) `pattern_provenance == "thresholded"`; (d) the harness obtained the matrix as a dense array and sparsified it. It is a **finite-difference fallback** if A18's count threshold trips, or if the numerically-zero entries of A11 are nonzero at S3/S4, or if CasADi's `enable_fd` was needed to proceed. Both are FAIL-composition, and both are recorded with the specific symptom, because P03's sparse-composition criterion is a hard criterion.

### 11.3 Manifest

`evidence/P02/<commit>/manifest.json`: `requirements: ["D02","D03","A05"]`; `status: tested` only if the judge ran to completion in the repository environment for at least the CasADi route and the Pyomo route is either `tested` or `BLOCKED` with evidence; `commands` = the actual `run.sh` invocations in each venv with exit codes and the `./scripts/check.sh` run; `checks` = one entry per `P02.<AID>.<backend>` and one per `P02.<MID>.<backend>` (result `pass` = recorded per protocol, `value` = the number); `artifacts` = the result directories by path and sha256; `limitations` must state that P02 is a composition test on a synthetic subsystem, not a solver test, not a performance benchmark on a real flowsheet, and not the backend selection; `review` left unset by the implementer (Fable reviews).

### 11.4 What P02 does not establish

Backend selection (P03). Correctness or convergence of any nonlinear solve. Scaling policy beyond the demonstration that the registered scales bring κ₂ from ~1e10 to ~1e2–4e2 on this subsystem. Phase-attempt behavior: the compiled formulation is fixed two-phase K-form and does not branch on the phase signature; S3/S4 show it is *evaluable and nonsingular* at single-phase solutions, not that it should be solved there. Empirical validity of anything (SYN-001 is synthetic). Timing on realistic problem sizes (17 variables measure overhead, not scaling). Whether a real property provider's declared sparsity is right (P02 declares its own).
