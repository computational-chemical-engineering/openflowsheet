## 0. The answer, in one paragraph

A study parameter is a pinned input already listed in `CompiledProblemMetadata.parameter_ids`. Its derivative `F_p` comes from a **parametric twin** — the same `ProblemSpec` compiled a second time with only the requested pinned inputs as CasADi symbols — which must reproduce the base problem's residual and Jacobian **bit for bit** at the state; the frozen `CompiledProblem`, its `Capabilities`, `model_version` and `constants_sha256` do not move (ADR 0031 D2). A sensitivity is issued only at a **qualified regular root**: converged, certified `VERIFIED`, [A08] screen `NO_RANK_LOSS_DETECTED` on the reduced square Jacobian, every TP phase split at least `τ_regime = 1e-4` from its phase boundary, and every requested parameter consistent with the eliminated alias rows; otherwise it is a typed refusal with no numbers (D3). Forward (`X = −J⁻¹F_p`) and adjoint (`Λ = −J⁻ᵀCᵀ`) solves share **one** factorization (D4). Sweeps are independent certified solves whose failed points are results (D5). The estimation example fits `(r, T_f)` of SYN-001 to seeded synthetic data: with a recycle-flow and mixer-temperature measurement it is identifiable; from the product streams alone the split fraction is **structurally unidentifiable** — derivation §5.1's recycle invariance — and the report must say so (D6). The A06 bridge is a PyNumero `ExternalGreyBoxModel` in **full space** over the twin, solved by cyipopt with Ipopt's **limited-memory** Hessian approximation (the exact Hessian is `absent` and a request for it is refused); the reported candidate is the decision vector, and everything claimed about it is recomputed on the **re-solved, certified simulation** at that decision, including a reduced-space KKT check built from M03's own adjoints (ADR 0032). Ipopt is an optional extra that exists only after an [A10] audit passes (§9); without it every optimization request is a typed `unsupported` result that names the audit.

## 2. Notation and conventions

- `x` — the ordered free variables (`variable_ids`, 47 for SYN-001); `p` — pinned inputs (`parameter_ids`, 10 for SYN-001); `F(x; p)` — the 49 compiled rows (`equation_ids`). `E` — the rows the plan's alias elimination removed (`tear.partition.elimination.eliminated`; for SYN-001 `U-FLASH:FLASH-P:inlet` and `U-SPLIT:SPLIT-P:recycle`), `K` — the kept rows in `equation_ids` order; `|K| = |x| = n`.
- **Scaling.** `S_x`, `S_F` — the K03 column and row scales (`Scaling.from_spec`, registered nominals: molar flow 3 mol/s, temperature 100 K, pressure 1e5 Pa, heat rate 1e5 W). `S_p`, `S_y` — the study's parameter and output scales, by the same quantity kinds (the split fraction is dimensionless with scale 1). Hatted quantities are scaled: `Ĵ = S_F,K⁻¹ F_x,K S_x`, `F̂_p = S_F,K⁻¹ F_p,K S_p`, and a scaled sensitivity is `Ŝ_kj = (∂y_k/∂p_j) · s_pj / s_yk`. **Every sensitivity tolerance in this document is on `Ŝ`.**
- `P_r = 100 000 Pa`; every registered state is at `P_r` with zero pressure drops.
- Parameter ids used here: `U-SPLIT.split_fraction` (r), `U-FLASH.T_spec` (T_f), `U-HEAT.T_spec` (T_h), `U-FEED.T_spec` (T_feed), `U-FEED.n_spec.A` (F_A); the refused pressure ids `U-FLASH.P_spec`, `U-FEED.P_spec`.
- Output ids are variable ids (`S4.N` = vapour product V, `S5.N` = flash liquid L, `S6.n.i` = recycle, `S7.n.A` = purge A, `S4.n.A` = vapour A, `S2.T` = mixer outlet T, `U-HEAT.Q`, `U-FLASH.Q`, `S3.V` = heater-outlet vapour) or **linear functionals** of them, written as `{variable_id: coefficient}` (`Q_total = {U-HEAT.Q: 1, U-FLASH.Q: 1}`, `recycle_total = {S6.n.A: 1, S6.n.B: 1, S6.n.C: 1}`). M03 needs no other output form.

## 3. Implicit sensitivities

### 3.1 Parameters (ADR 0031 D1)

A study parameter is an element of the compiled problem's `metadata.parameter_ids`, declared by the study with a finite domain `[lower, upper]` and a scale. Nothing else is a parameter: a variable is never "freed" into a parameter by a study (that is a different declaration, T04's binding), and a parameter is never promoted to a variable. An id not in `parameter_ids` is refused `UNKNOWN_PARAMETER`.

### 3.2 The parametric twin (ADR 0031 D2)

`F_p` is produced by compiling the problem's own `ProblemSpec` a second time, inside `compile/casadi_backend.py` (ADR 0003 D5.7: the only CasADi importer), with the requested parameters as `ca.MX` symbols and every other pinned input as the same Python float the base problem baked in. The twin exposes, for a state `x` and requested-parameter values `p_P`:

- `residual(x, p_P)` — the 49 rows;
- `jacobian_x(x, p_P)` and `jacobian_p(x, p_P)` — sparse CSC, rows `equation_ids`, columns `variable_ids` and the requested ids, from `ca.jacobian` of the same expression graph;
- its identity: `model_version` (computed exactly as the base computes it — it must be equal) and `constants_sha256(p)` for the full pinned-input vector at `p_P`.

**Identity guard (assertion A01).** At every state where a sensitivity is requested, after signed-zero normalization (`v + 0.0`): `twin.residual(x*, p₀) == base.residual(x*)` element for element, and `twin.jacobian_x(x*, p₀) == base.jacobian(x*)` entry for entry, with `p₀` the base's own pinned values. A difference of any size refuses the request `TWIN_MISMATCH` — it is a defect, not a tolerance. *Measured:* bitwise equal at P1, P2 and P3 for the residual and for all 49 × 47 Jacobian entries, with seven pinned inputs symbolic (the five registered parameters and both pressure specifications), and at P1 also with all ten symbolic.

**Why this is "the same function at the same state"** (CLAUDE.md): the twin is built from the identical `EquationSpec.build` callables, block callbacks and variable symbols; it differs from the base only in whether a pinned input enters the graph as a symbol or as a constant, and the guard checks the consequence rather than assuming it.

**A builder that cannot take a symbolic parameter** (one that branches on, or converts, a parameter's Python value) makes the twin construction raise; the request is refused `PARAMETER_NOT_DIFFERENTIABLE` naming that parameter, never retried with finite differences. The base problem, its `metadata`, `Capabilities`, `model_version` and `constants_sha256` are untouched: nothing in K05's identity document, SYN-001's structural hash or any T06 value can move.

### 3.3 The reduced system

At a state `x*` the sensitivity system is the K04 target: rows `K`, all columns, scaled by `S_F,K` and `S_x` — **the same matrix the [A08] screen judges** (K04 §7.1). It is square (`n × n`); a non-square reduced system is refused `UNSUPPORTED_RANK_STRUCTURE` (the K03 precedent), recorded as Q2 failing with the reduced shape in its detail, before and instead of the screen (a rank screen of a rectangular matrix answers a different question); Q3 is then `not_evaluated` (A45; *Amendment 1*: the code was named here but missing from ADR 0031 D3's list, which now carries it). The eliminated rows are not part of the solve but are checked (§3.5, Q3).

### 3.4 Phase-regime margins

For every **TP-type** lifted split (ADR 0012 D3) — on the SYN-001 tear path the heater outlet (`U-HEAT`, stream S3) and the flash (`U-FLASH`, streams S4/S5) — let `n` be the split's inlet component flows (heater: S2; flash: S3), `(T, P)` its specified temperature and pressure, `K_i = exp(lnK_i(T, P))` from the flowsheet's property provider, and `z_i = n_i / Σn` over the components with `n_i > 0`. With `s₁ = Σ z_i K_i − 1` and `s₂ = Σ z_i / K_i − 1`:

| Regime | Condition | Margin `m` |
| --- | --- | --- |
| `LIQUID` | `s₁ ≤ 0` | `−s₁` |
| `VAPOR` | `s₂ ≤ 0` | `−s₂` |
| `TWO_PHASE` | otherwise | `min(s₁, s₂)` |
| `ZERO_FLOW` | `Σn = 0` | `0` |

`m` is dimensionless and continuous across each boundary (at the bubble point `s₁ = 0` on both sides). The derivation's §5.1 shows `s₁, s₂ > 0` for the flash feed exactly when they are for the fresh feed, which the generator checks at every registered state (claim C3).

**Why `τ_regime = 1e-4`.** *Measured* along SYN-001's bubble point (r = 0.5, T_f = T_b + δ, δ from ±1e-1 to ±1e-5 K): the target's `rcond₁` is linear in the margin, `rcond₁ ≈ 0.021 m` on the two-phase side and `0.011 m` on the liquid side, and the [A08] screen turns `ILL_CONDITIONED` (K04's `τ_ill = 1e-8`) at `m ≈ 5e-7` to `1e-6`. A threshold of `1e-4` therefore (i) is eleven orders above the binary64 classification noise ADR 0017 deals with, (ii) refuses on the *regime* while the Jacobian is still demonstrably regular (rcond₁ ≥ 1e-6), so that the refusal is attributed to the boundary rather than left to a conditioning accident, and (iii) corresponds to a parameter distance of about 7.5e-3 K in T_f at the bubble point (`∂s₁/∂T ≈ 1.34e-2 K⁻¹`), inside which blueprint §6.3's "derivatives may be one-sided, nonsmooth, or undefined" is a live risk. It is a policy constant of `M03-sensitivity-v1`; a different value is a new policy id, never a per-call override (blueprint §8.1: a study cannot relabel).

A **PH-type** split is refused `REGIME_MARGIN_UNSUPPORTED` (M03 defines no margin for the saturation band of ADR 0012). A `ZERO_FLOW` split has margin 0 and is refused `PHASE_BOUNDARY`.

*Amendment 1.* A request is answered by a `SensitivityResult` for every state vector of the right length: nothing a state or a factorization can do escapes as an exception (Q1's unevaluable residual, Q2′'s failed solve). Only a malformed request raises — a state vector of the wrong length, an output naming an unknown variable — and so does a property-provider failure at a split's own specified `(T, P)`, which the flowsheet's construction has already validated and which is therefore a defect, not a state.

Q3 is the finding of the 2026-10-08 probe: a pressure specification alone moves a pressure that an eliminated alias row ties to the other specification, so `∂x/∂p` for it alone is the derivative along a direction that leaves the solution set. Combined directions (both pressures together) are consistent but M03 does not offer directional requests; this is recorded in §15.

### 3.6 Forward and adjoint (ADR 0031 D4)

With `Ĉ = S_y⁻¹ C S_x` (the outputs' coefficient matrix, scaled):

- **forward:** factorize `Ĵ` once (`numerics.linear.solve_linear_kept`, ADR 0004 options and record) and solve `Ĵ X̂ = −F̂_p` for all requested columns at once; `Ŝ_fwd = Ĉ X̂`.
- **adjoint:** solve `Ĵᵀ Λ̂ = −Ĉᵀ` **on the same factorization** — a new `KeptFactorization.solve_transposed`, which calls SuperLU's `solve(b, trans="T")` and records and judges its residual against `Ĵᵀ` exactly as ADR 0004 D3 judges the forward solve; `Ŝ_adj = Λ̂ᵀ F̂_p`.
- **both:** both, from the one factorization, and the consistency identity `Ŝ_fwd ≈ Ŝ_adj` (blueprint §5.2's `vᵀ(Ju) = (Jᵀv)ᵀu` with `v = Ĉ_k`, `u = X̂_j`) is checked and recorded per entry (assertion A07).

*Amendment 1 — what each mode solves.* Mode `adjoint` still performs the forward solve `Ĵ X̂ = −F̂_p` on the one factorization, because Q3 is a statement about `X̂` (`Ĵ_E X̂_j + F̂_p,E,j`); its values are a qualification input, are not published (the result has no `forward` block), and its `LinearSolveRecord` is recorded beside the transposed one. Mode `forward` performs no transposed solve. Neither adds a factorization (A10).

*Amendment 1 — the consistency record never refuses.* In mode `both` the record is `consistency = {max_abs_difference, tolerance, within_tolerance}` with `tolerance = τ_abs + τ_rel max|Ŝ_fwd|` over the qualified columns; `within_tolerance: false` does **not** change `status`. Reason: both solves are already judged individually against their own matrices (ADR 0004 D3, Q2′), and in exact arithmetic `Ŝ_fwd = Ŝ_adj`, so their difference is bounded by the two solves' forward errors, of order `κ(Ĵ) ε max|Ŝ|`. Q2 accepts conditioning up to `κ ≈ 1e8`, where that bound reaches ~1e-8 relative — above `τ_rel` — so refusing on consistency would be a second, undeclared conditioning threshold near `κ ≈ 1e6`, contradicting Q2's registered `τ_ill`. The record is evidence about the solves' accuracy; A07 judges it at the registered states (rcond₁ ≥ 1.33e-4, κ₁ ≤ 7.6e3), and a consumer must not read `QUALIFIED` as `within_tolerance`.

The number of `numerics.linear.factorize` calls a request makes does not depend on the number of parameters or outputs: one for the [A08] screen (K04 §7.5 makes the screen factorize what it judges) and one for the solves (assertion A10; ADR 0004's "one factorization" and the brief's performance invariant). The unscaled sensitivity reported beside `Ŝ` is `S = S_y Ŝ S_p⁻¹`.

**Finite differences are a test oracle only** (R-010): no production path computes `F_p` or `S` by differencing, and assertion A03 makes the call counts prove it.

### 3.7 The result record

`SensitivityResult` (and the `sensitivity_result` `$def` of §10): `policy_id = "M03-sensitivity-v1"`; the pairing identity of the base evaluation at `x*` (`model_version`, `constants_sha256`, `state_sha256`, `phase_signature`); `parameters` (ordered ids with scales and per-column status and refusal); `outputs` (ids, coefficient maps, scales); `mode`; `status`; `refusals`; `qualification` (the Q0–Q4′ outcomes in §3.5's order, Q2′ included; `scaled_residual_inf`; the K04 `RegularityEvidence` document; each split's regime and margin; each column's alias residual); `forward` and/or `adjoint` blocks with `scaled` and `unscaled` matrices (rows outputs, columns parameters; `null` where refused); `consistency` (`{max_abs_difference, tolerance, within_tolerance}` when mode is `both`, §3.6; recorded, never a refusal); the `LinearSolveRecord`s; `derivative_provenance = "implicit-exact"` (blueprint §5.2's declaration: the derivative is implicit from exact first derivatives, through the opaque property callbacks' declared Jacobians). Sensitivity results are **not** part of any replay bundle in M03; their identity is the pairing identity plus the request, and on one platform they are bitwise reproducible.

## 4. SYN-001 closed forms and registered states

### 4.1 The flowsheet map

From derivation §5.1 (valid in every regime; §7's single-phase variants are its special cases), with `z = F/F_tot` the fresh-feed composition and the fresh-feed TP flash at `(T_f, P_r)` giving `β`, `x_i = z_i / (1 + β(K_i − 1))`, `y_i = K_i x_i`:

```
V = β F_tot                    S4.n_i = V y_i
purge_i = F_tot (1 − β) x_i    S7.n_i = purge_i            (independent of r)
L = F_tot (1 − β)/(1 − r)      S5.n_i = L x_i
t_i = r L x_i                  S6.n_i = t_i                 t_tot = r L
T_mix = (F_tot T_feed + t_tot T_f) / (F_tot + t_tot)         (§4.1; both inlets liquid)
H1 = c_p (T_feed − T_r) F_tot,   H6 = c_p (T_f − T_r) t_tot
H3 = c_p (T_h − T_r)(F_tot + t_tot) + Σ_i L_i v_i^heater      (heater split of F + t at (T_h, P_r))
H4 = c_p (T_f − T_r) V + V Σ_i y_i L_i,   H5 = c_p (T_f − T_r) L
Q_h = H3 − H1 − H6,   Q_f = H4 + H5 − H3,   Q_total = Q_h + Q_f = c_p(T_f − T_feed) F_tot + V Σ y_i L_i
```

where `v_i^heater` is the vapour of the heater's TP split (zero when it is `LIQUID`). The generator evaluates these at 60 digits and differentiates them by central differences at `h = 1e-20 · s_p` (truncation and roundoff both below 1e-38 relative); claim C1 checks the 2nd- against the 4th-order difference to 1e-30 (scaled) at every state, and claim C1′ checks `dV/dT_f = −F_tot RR_T/RR_β` from the implicit function theorem against the difference derivative to 1e-30.

### 4.3 Structural zeros, derived

The JSON lists, per state, every `(output, parameter)` whose closed-form sensitivity is below 1e-35 and labels it `universal` (zero at all three states) or `state_specific`. Each universal zero has a one-line derivation:

## 6. Sweeps (ADR 0031 D5)

A sweep is a study over one declared parameter and an ordered list of values. **Semantics:**

1. Each point is an independent solve of the flowsheet with that pinned input replaced, from the case's registered initializer (`start = "registered_initializer"`, a single-valued literal; a later chaining mode is a new value). No point's start depends on another point, so the result is independent of the order of the list (assertion A23).
2. Each point is then certified (K04 `verify`) and, when requested, given a sensitivity (§3).
3. **A failed point is a result**: an exception at construction or a non-converged solve is caught and recorded with a typed outcome (`SPECIFICATION_REFUSED`, the K03 outcome codes, `CERTIFICATE_NOT_VERIFIED`) and its first message line; its outputs are `null`. The sweep never drops, interpolates or repeats a point, and never stops early except on its budget, in which case its status is `INCOMPLETE` and the unrun points are listed as `NOT_RUN`.
4. What a sweep may claim: per point, what that point's records claim. It claims nothing between points — no continuity, monotonicity, or branch connectivity. Each point records its root fingerprint (`orchestrator/roots.py`) so a branch change is visible rather than inferred.

*Amendment 1 (confirming the build).*

- **The budget is a point count**, `max_points ≥ 0`: once that many points have run, the rest are `NOT_RUN` (A24). A wall-time budget would make a point's fate depend on the machine, which A23's order-independence forbids.
- **There is no interrupt path in M03.** A sweep runs in the study runtime, not as an application job. An interrupt (`KeyboardInterrupt`) propagates and produces **no** `SweepResult`, so no partial result can be read as complete. If sweeps become jobs, cancellation belongs to ADR 0020's job lifecycle and records the unrun points `NOT_RUN`.
- **There is no study-level domain pre-check.** The domain a value must lie in is the model's, enforced when the unit is constructed (the 445 K point is `SPECIFICATION_REFUSED` by the flash, as measured). A second copy of the domain in the sweep could drift from the model's. The study parameter's declared `[lower, upper]` (§3.1) is recorded with the sensitivity request and is not a qualification: a sensitivity is local at the given `p`, and M03 checks no qualification against that interval (§3.5 lists none).
- **An ill-formed request raises before any point runs.** This covers an id that is not a pinned input (`KeyError`), an empty value list, a negative budget, and a pinned input SYN-001 cannot move alone at a value other than its current one (`ValueError`; §8.7, the pressure specifications). Such a request describes no member of the flowsheet family, so it is not a point that failed.

### 7.2 The synthetic data, byte-reproducible

The noise is generated by the reference generator, not by any library whose stream may change: SplitMix64 with seed 20261008 (the standard constants `0x9E3779B97F4A7C15`, `0xBF58476D1CE4E5B9`, `0x94D049BB133111EB`), `u_k = ((w_k ≫ 11) + ½) · 2⁻⁵³ ∈ (0, 1)`, `e_k = √2 · erfinv(2u_k − 1)` at 60 digits, `y_obs,k = binary64(y_k(θ*) + σ_k e_k)`, in the table's order (10 draws). ### 7.3 The estimator

Weighted least squares, `min ½ Σ_k ((y_k(θ) − y_obs,k)/σ_k)²`, by `scipy.optimize.least_squares(method="trf", jac=<M03 sensitivities>, bounds=…, x_scale=(1, 100), ftol=xtol=gtol=1e-14, max_nfev=100)`. Each residual evaluation is a production solve of the flowsheet at θ from the registered initializer and a K04 certificate (`VERIFIED` required); the Jacobian is M03's **forward** sensitivity at the same state (`QUALIFIED` required). Evaluations are cached on the exact θ tuple (CLAUDE.md: exact caches key on exact inputs). A refused certificate or sensitivity at an iterate ends the fit `FAILED` with that refusal; no fallback derivative exists. *Amendment 1:* so does an estimator that did not converge. When `least_squares` returns `status ≤ 0` (0: `max_nfev` reached; −1: improper input), the fit is `FAILED` with the code `ESTIMATOR_NOT_CONVERGED` (stage `estimator`). The report records the estimator's status, message, `nfev`, `njev` and the last iterate, and carries no estimate, standard error, covariance, identifiability verdict or prediction (A46). Statuses 1–4 (`gtol`, `ftol`, `xtol`, both) are convergence; which one fired is recorded.

### 7.4 Identifiability, covariance, validation

At the final θ̂ (and, recorded, at θ₀): `J̃ = W^{½} J S_θ` (rows weighted by 1/σ_k, columns scaled), its singular values `σ₁ ≥ σ₂` and right singular vectors.

- `rank = #{σ_i > τ_id σ₁}`, `τ_id = 1e-8` (K04's `τ_ill`, for the same reason: beyond κ = 1e8 the data cannot distinguish a parameter combination). `IDENTIFIABLE` iff rank = 2; else `UNIDENTIFIABLE`, with each null direction (right singular vector of a σ below the threshold) reported in scaled coordinates, sign fixed so its largest component is positive.
- A parameter is `determined` iff its component in every null direction is below 1e-6 in magnitude. Only determined parameters get an estimate; an undetermined one is reported as `final_iterate` with `determined: false` and **no** standard error.
- *Amendment 1 — an undetermined parameter is not held, and its final iterate is arbitrary.* The estimator moves every parameter. Along a null direction the data exert no force, so the final iterate there is set by the optimizer's path: its trust region, its bounds, and the roundoff in a Jacobian column that is zero in closed form. It is not set by the data. *Measured:* FIT-U's r went from 0.6 to 0.96906, inside the bound 0.97 but not at it. Consequently:
  - The `final_iterate` of an undetermined parameter is recorded for provenance only (it says where the reported state was evaluated). It is checked only to lie inside the parameter's bounds, and nothing may be derived from its value.
  - Every reported quantity of an unidentifiable fit is one of three kinds. (i) **Invariant along the null directions**, so it may be reported with a value and registered: the determined estimates, the singular values and null directions, χ², `dof`, and the value of a determined prediction. (ii) **Undefined**: the undetermined parameters' estimates and standard errors, the covariance, the correlation, and an undetermined prediction's value. (iii) **A diagnostic that depends on where the iterate stopped**: an undetermined prediction's null projection. It is reported, but registered only as its range over the box.
  - The generator therefore holds r at θ₀ in its FIT-U fit. Claims C9[FIT-U] show this changes nothing in class (i): on the grid r = 0.50, 0.51, …, 0.97 at T̂_f, every FIT-U measurement, its θ-Jacobian and S4.N are independent of r. The claims also show that the class (iii) range keeps `determined: false` wherever r ends.
  - Holding undetermined parameters, or projecting the step onto the identifiable subspace, is not offered in M03 (§14 D-3). A held parameter needs the identifiability decision before the fit. A projection needs a null space that does not turn with θ. Neither is needed to decide the registered fits.
- When `IDENTIFIABLE`: `Cov = S_θ (J̃ᵀJ̃)⁻¹ S_θ` (`covariance_basis = "declared_sigma"`, not rescaled by χ²/dof), standard errors, correlation; χ² and `dof = m − rank`.
- Validation: for each held-out output v, the prediction `v(θ̂)`; when identifiable its standard error `√(∇v Cov ∇vᵀ)` and the normalized residual `(v_obs − v̂)/√(σ_v² + SE²)`. When unidentifiable, a prediction is `determined` iff `|∇̃v · n| ≤ 1e-3 ‖∇̃v‖` for every null direction n (∇̃v the scaled gradient); an undetermined prediction gets no value.

### 8.1 The registered problems

**NLP-1.** Decisions d = (`U-SPLIT.split_fraction` ∈ [0.50, 0.97], scale 1; `U-FLASH.T_spec` ∈ [356, 366] K, scale 100 K) — the §7.1 box. Objective (dimensionless):

### 8.2 Formulation: full space over the twin

- **Variables:** all 47 state variables and the decisions. **Equality constraints:** the 47 kept rows `F_K(x; p(d))`, evaluated by the parametric twin with the decisions symbolic (the base compiled problem bakes the start's decisions and is not used during the solve). **Jacobian:** `[F_x,K  F_p,K]` from the twin, exact. Decisions that fail Q3 (alias consistency, §3.5) at the start are refused `DECISION_INCONSISTENT_WITH_ELIMINATED_ROWS` before any solve.
- **Objective and inequality constraints:** declared as linear or quadratic expressions of named variables (no other form in M03), placed in the Pyomo model as an `Objective` and `Constraint`s with explicit bounds — never as penalty terms (blueprint §10: a penalty is not constraint satisfaction).
- **Bounds** ("true domain restrictions"): decisions — their box; temperatures — [280, 440] K, pressures — [5e4, 2e5] Pa (the provider's declared domain, outside which a property block refuses); molar flows — lower bound 0, **except** a flow variable whose value at the verified start is exactly 0.0, which is left unbounded. Such a variable is pinned at zero by the declared regime's own rows (the liquid heater's vapour, S3.vap.i and S3.V); a bound there would be weakly active with a linearly dependent gradient and break LICQ, while the equations already determine it. If the regime were to change, the unbounded variable is free to go negative, which the verification of §8.5 then catches (V2, V4). Heat rates are unbounded.
- **Scaling:** Ipopt user scaling — variables 1/S_x, decisions 1/s_d, equality rows 1/S_F (the K03 nominals), objective 1, `recovery_A` 1 (already scaled).
- **Initial point:** the verified simulation state at the start decisions.
- **Evaluation failures:** a property block's domain or block error during an Ipopt evaluation is raised through PyNumero's evaluation-error mechanism so that Ipopt rejects the trial point (needs a fact, §14 Q-F4); never a NaN, never a clipped value.

### 8.3 Hessian policy

`Capabilities.hessian` is `absent` and stays so (ADR 0003 D5.4). The adapter sets `hessian_approximation = limited-memory` with `limited_memory_max_history = 6` and records both in the report as `{"capability": "absent", "approximation": "ipopt-limited-memory", "history": 6}`. A request for an exact Hessian is refused `HESSIAN_UNAVAILABLE` before any solver call. No finite-difference, Gauss–Newton or zero Hessian is ever supplied. Consequence for the claims: second-order conditions are **not assessed** (`second_order = "not_assessed"`), except that at a vertex — active set size equal to the number of decisions, LICQ, every multiplier > 1e-8 — the critical cone is {0} and first-order evidence suffices (`"vacuous_at_vertex"`). NLP-1 is not a vertex (one active constraint, two decisions); its expected value is `"not_assessed"`. ADR 0003's trigger T5 (a second-order requirement M03 cannot meet on CasADi) does not fire: M03's requirement is met by the approximation plus independent verification.

### 8.5 Verification: termination is not feasibility, stationarity is not optimality

The **candidate is the decision vector d** returned by a start; everything the report claims is computed on the **re-solved simulation** at d, not on Ipopt's state:

- **V1** Re-solve the flowsheet at d with the production solver from the registered initializer: `CONVERGED`, and the K04 certificate `VERIFIED`.
- **V2** Gross-error check of Ipopt's state: `‖S_x⁻¹ (x_ipopt − x_sim)‖_∞ ≤ 1e-6`. It catches a different branch or a negative-flow pseudo-solution (O(1e-2) or more); it is not a precision claim. *Amendment 1 (confirming the build):* V2 is defined only against an optimizer's state. Called without one, the verifier records V2 `not_evaluated` (reason `no optimizer state supplied`), and the candidate is therefore never `passed`: a point no optimizer produced cannot be `KKT_POINT_VERIFIED`. This is why A32, which verifies the reference optimum without Ipopt, asserts the V1 and V3–V5 outcomes and the V5 numbers, plus V2 `not_evaluated` and `passed = false`, not an overall status.
- **V3** Decisions inside their bounds exactly; every inequality on `x_sim`: `ĝ ≥ −τ_feas`, `τ_feas = 1e-8` (scaled; 3e-8 mol/s, inside K04's flow tolerance); constraint values and slacks reported; active set `A = {i : |ĝ_i| ≤ 1e-6}` ∪ the bounds within 1e-6 (scaled).
- **V4** Every TP split's regime at `x_sim` equals the formulation's (the start's) and its margin is `≥ τ_regime`.
- **V5** Reduced KKT, independent of Ipopt: the scaled gradients of φ and of every active g with respect to the decisions, from M03's **adjoint** sensitivities at `x_sim` (`QUALIFIED` required); multipliers by least squares on the active set (`∇φ̂ = Σ μ_i ∇ĝ_i + ν_L − ν_U`); stationarity residual `‖·‖_∞ ≤ τ_KKT = 1e-6`; signs `μ_i, ν ≥ −1e-8`; LICQ (smallest singular value of the active gradients ≥ 1e-8 of the largest). `second_order` per §8.3.
- **V6** Objective and constraint values recorded from `x_sim`.

**Statuses** (`OptimizationReport.status`): `KKT_POINT_VERIFIED` — V1–V5 pass for the candidate; `NOT_VERIFIED` — a start returned a point and a V check failed (each failure listed); `INFEASIBLE_REPORTED` — no start produced a verified point and at least one ended in Ipopt's infeasibility statuses; `SOLVER_FAILED` — no verified point and none reported infeasibility; `UNSUPPORTED` — refused before any solve (reasons of §8.7). Ipopt's own return status is recorded for every start and is never sufficient for `KKT_POINT_VERIFIED`.

*Amendment 1 — per-start classification and precedence (the ruling WO-8 implements).* V1–V6 run on the decisions every start returns, whatever Ipopt's return status. Ipopt's status is read as the integer `ApplicationReturnStatus` that cyipopt reports (`info["status"]`), with its message. Each start is classified by the first rule that applies:

| # | Rule | Start classification |
| --- | --- | --- |
| 1 | V1–V5 all `pass` | `KKT_POINT_VERIFIED` — whatever Ipopt's status: the truth decides, and Ipopt's status is neither sufficient nor necessary |
| 2 | Ipopt's status is `Solve_Succeeded` (0) or `Solved_To_Acceptable_Level` (1) | `NOT_VERIFIED` — Ipopt claimed a solution and the re-solved simulation refuted it; the failing V checks are listed |
| 3 | Ipopt's status is `Infeasible_Problem_Detected` (2) | `INFEASIBLE_REPORTED` |
| 4 | anything else: every other status, an evaluation error that ended the run (§14 Q-F4), an exception in the adapter, no returned decisions | `SOLVER_FAILED` (V checks that cannot run are `not_evaluated`) |

The report's `status` is the highest-precedence start classification: **`KKT_POINT_VERIFIED` > `NOT_VERIFIED` > `INFEASIBLE_REPORTED` > `SOLVER_FAILED`**. When `NOT_VERIFIED` and `INFEASIBLE_REPORTED` both apply, the report is `NOT_VERIFIED`. A refuted claim of success is the most specific evidence the run produced, and Ipopt's infeasibility verdict is local and heuristic. Masking the refutation behind it would let "the problem may be infeasible" stand in for "the optimizer's answer is wrong". Infeasibility is the report's status only when no start produced a point that Ipopt itself accepted. Every start record carries its `classification`. For every status other than `UNSUPPORTED`, `reasons` lists, in start order, one entry for each start not classified `KKT_POINT_VERIFIED`: its classification as the code, Ipopt's status name and the failing V checks as the detail, and `start <i>` as the subject. A refuted claim at one start is therefore visible beside a verified candidate at another. The candidate is `null` unless the status is `KKT_POINT_VERIFIED`. `claims.local_stationarity` is true exactly then. The classification and the aggregation are one pure function of `(Ipopt status, V1–V5 outcomes)` per start, in default-gate code that imports no third-party solver (A47). The candidate is the verified start with the lowest objective (first in start order on a tie); `distinct_local_solutions` counts verified decisions more than 1e-6 apart (scaled, greedy in start order). `claims = {"global_optimality": false, "local_stationarity": true or false, "second_order": one of §8.3's two values}`. Blueprint §10: local stationarity is not global optimality, and three starts are evidence of nothing global.

**Why `τ_KKT = 1e-6` is consistent with the decision tolerance:** at NLP-1 the free direction's curvature is 534, so a stationarity residual of 1e-6 means |Δr| ≈ 2e-9; Ipopt at `tol = 1e-10` is predicted to leave |Δr| ≈ 2e-13. At the start (0.6, 360 K) the reduced gradient in r is O(1), so the check discriminates.

### 8.6 The `OptimizationReport`

Fields (blueprint Appendix A: "model/study hash, candidate, feasibility, stationarity evidence, truth evaluations, domains, starts, budget and limits"): `schema_version = "optimization-report-v1"`; `formulation` (decisions with bounds and scales, objective and constraint expressions, `"full_space"`, the declared regimes); `model` (`model_version`; the base `constants_sha256`); `solver` (`ipopt` version, `cyipopt` version, `pyomo` version, linear solver, the §8.4 options verbatim, the [A10] audit id and verdict); `hessian_policy` (§8.3); `starts` (each: start decisions, Ipopt return status and message, iterations, evaluation counters `residual_calls`, `jacobian_calls`, `property_calls`, wall time, final decisions, Ipopt's final primal/dual infeasibility and complementarity, its V1–V6 outcomes, and its `classification` (§8.5, Amendment 1)); `candidate` (decisions, objective, constraint values and slacks, active set, multipliers, stationarity residual, LICQ, `second_order`, the certificate id and `state_sha256` of `x_sim`); `distinct_local_solutions`; `status` (§8.5's precedence); `reasons` (§8.7's for `UNSUPPORTED`, otherwise one per start not classified `KKT_POINT_VERIFIED`); `claims`; `limits` (`max_iter`, `max_wall_time`, the regime restriction, "Hessian absent").

### 8.7 The optimization closure (D16's M03 half) and unsupported paths

*Amendment 1 — what `SIMULATION_NOT_READY` covers (confirming the build).* It is one code for "the simulation at a start is not a qualified root the formulation can stand on". ## 15. What this specification does not establish

- **No empirical validation.** The estimation data are generated from the model; FIT-I's agreement with θ* verifies the machinery, not SYN-001 against anything real (SYN-001 is synthetic).
- **No global optimality**, and no second-order optimality for NLP-1 from the implementation (the Hessian is absent). The reference's strict local minimum and its uniqueness on the box are closed-form and grid facts about the reference, not about what Ipopt is shown to find elsewhere.
- **No coverage beyond the registered hosts.** Sensitivities are specified for TP-type splits on SYN-001's tear path. Revision-built (EO) flowsheets, PH-type splits, zero-flow splits and the kinetic CSTR (multiple steady states) are refused by type or not exercised; nothing here says their sensitivities are right.
- **No proof of the regime and uniqueness claims.** C10 and C12 are grid checks (21 × 21 and 41 × 21); they bound the risk, they do not exclude a regime change between grid points.
- **The FD oracle is not validation.** It shares the production solver and property backend with the implicit path (blueprint §5.2: a consistency test, not independent validation); the closed form is the independent expectation.
- **The toys test the refusal mapping, not the K04 screen.** K04's tests own the screen.
- **A sweep claims nothing between its points.**
- **An undetermined parameter's reported value is not an estimate** (Amendment 1). FIT-U's r = 0.969 says where the optimizer stopped, not what the data say. The registered FIT-U values are invariant along r on a grid (C9), which is a grid check and not a proof.
- **The forward–adjoint consistency record is not a qualification** (Amendment 1). `QUALIFIED` does not imply `within_tolerance`.
- **The [A10] verdict is not a legal opinion.** It records what is loaded and what the notices say; accepting the licences is Frank's (N1).
- **Nothing here is a trust-region result** (M05) or a surrogate result (M04); a cyipopt success does not complete M05 (plan L271).
