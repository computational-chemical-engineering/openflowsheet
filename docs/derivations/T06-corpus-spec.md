## 3. The corpus

### 3.1 Rules

1. **A case is a distinct scientific failure mechanism**, registered once (plan §6.1). Variants of one mechanism are one case: SYN-001's r-variants are NET-01 (plan §3.2, §4.3); A02's 355/360/365 targets are NET-05; T05b's DZ-1/DZ-2 are STA-01's family. A case may cite several fixtures; it is counted once.
2. **Every case names its fixture** — a registered revision, a reference-file key, or a test node — and **its expected outcome kind**: `verified_at_reference` (`CONVERGED`, certificate `VERIFIED` under `K04-check-policy-v1`, the certified state within T02 §6.4's allowances of the registered root on every registered coordinate), `converged_to_closed_form` (a synthetic problem with no certificate by construction), `typed_failure(<outcome>)`, `validation(<status>, <check>, <implicated>)`, `binding_refusal(<kind>, <code>)`, `construction_refusal(<code>)`, `certificate(<verdict>, …)`, `regularity(<status>)`, `structural_finding(<finding>)`, `multiple_roots`, `invariant`, `noise_levels`.
3. **The success denominator** (blueprint §13.4 "all fixed nominal correctness fixtures pass") is the cases of kind `verified_at_reference` or `converged_to_closed_form`: **30 (A1; 28 before STA-03 and STA-04 became solved cases)**. Every other case is outside it by this preregistered classification and is judged by its own outcome.
4. **Ensemble eligibility** (§6.1) is a separate flag.
5. **Plan IDs keep their meaning.** Where an earlier specification used a plan ID for a fixture of a different mechanism, the corpus ID is the plan's and the fixture keeps its old name: K03's seed `NUM-01` (`x − 2` from `x⁰ = 2`) is an *exact initial root*, so it supports corpus NUM-04, while corpus NUM-01 is K03's `BND-01`.

### 4.4 ADV-06 — the noisy callback

A provider test double **`NoisyProvider(level)`** wraps `Syn001Provider`: every value `evaluate_phase` returns for a molar enthalpy gets `η_h · ξ` and for an `lnK_<c>` gets `η_K · ξ`; derivatives are returned unchanged; `flash` is unchanged. `ξ = 2u − 1` with `u` §6.3's draw of the key `"T06-ADV-06|" + level + "|" + phase + "|" + output + "|" + hex(IEEE-754 big-endian bytes of n_A, n_B, n_C, T, P)`. The noise is therefore a deterministic, rough function of the exact request — which is what a loosely converged external callback is — so the exact property cache stays consistent. It is bound into C1 (`SYN-001-UL-C1`) so that **every evaluation the compiled blocks, the traversal and the verifier's compiled residual make sees it**; whether the verifier's fresh flashes see it is recorded (they call `flash`, which is clean). No frozen interface changes: the double implements `PropertyProvider`; the injection point is a test hook.

| Level | `η_h` (J/mol) | `η_K` | Largest energy-row noise, scaled | Witness error scale | Expected |
| --- | --- | --- | --- | --- | --- |
| H | 10 | 1e-3 | ≥ 4.1e-6 (≥ 400 τ̂) | — | never `VERIFIED` or `RELAXED`; any typed failure, `FAILED` or `UNVERIFIED` |
| M | 1e-5 | 1e-11 | ≤ 6e-10 (τ̂/16) | 6e-5 (600× K04's 1e-7) | `CONVERGED`; `UNVERIFIED`; its only limitation is `derivative_limitation` (A1; the shared-provider qualification is `independence_qualifications`, §8.4); every K04 §4.1–§4.7 check `pass` |
| L | 1e-10 | 1e-15 | ≤ 6e-15 | ≤ 6e-10 (tol/167) | `CONVERGED`, `VERIFIED` |

The argument (generator-checked, `ref.closed_form.adv06_noise_bands`): a C1 energy row sums at most 6 mol/s of enthalpy flows, so its noise is at most `6 η_h` W, scaled by 1e5 W; K04 §4.8's witness differences the compiled function at `±1e-5` scaled steps, so a row noise `ν` gives a witness error of order `ν / 1e-5`. At M the noise is 16× below the residual tolerance and 600× above the witness tolerance; the chance that every stencil pair of the largest row escapes detection is below 1e-20 (claim `ADV-06.M.escape_probability_below_1e-20`, independent draws at the ≥ 20 stencil states of ≥ 10 columns). At L both are orders below. Three levels so that no single rule can pass all three: a verifier that ignores the witness passes M; one that fails everything noisy fails L.

## 6. The ensemble and the sampling law ([A04])

### 6.1 Eligibility

A corpus case is **eligible** iff (a) its expected outcome is `verified_at_reference`; (b) it is a flowsheet on SYN-001's thermodynamics (not a synthetic map); (c) its registered start space is not degenerate; (d) it is not linear in every free coordinate (a linear problem converges in one Newton step from anywhere, so its 20 starts carry no information and would inflate the rate); (e) **(A1)** it is not a metamorphic restatement of another case — its compiled problem and start are not another eligible case's (NUM-04 starts at NET-01's root; STA-03's converted revisions compile to NET-01's declaration and STA-04's mapped revision to NET-08's, bit for bit), because its starts would re-sample that case's basin under another name and count it twice. Eligibility is decided on the definition and on the registered-initializer solve, **never on an ensemble outcome**.

**22 eligible** (the ✓ column of §3.2). **Excluded, with the reason:** NUM-01, NUM-02, NET-04, ADV-05 (synthetic); NUM-04 (starts at the root); **STA-03, STA-04 (A1: metamorphic restatements of NET-01 and NET-08; their mechanism lives in the binding and is exercised completely by their registered solves)**; ADV-01 (its registered start is adversarial by design); **THM-04** — its tear stream is dormant at the initializer and, at 420 K and `P_r`, `min_i K_i = K_C = 1.65 > 1` (generator-checked), so every nonzero liquid-labelled recycle is inadmissible to the mixer (R-007) and the tear path's start space is the single point `t = 0`.

### 6.3 The draw

`u(key)` = the first 8 bytes of SHA-256 of the key (UTF-8), read big-endian, shifted right by 11, times 2⁻⁵³ — a 53-bit uniform on `[0, 1)`; `δ = 0.2 · (2u − 1) ∈ [−0.2, 0.2)`. `2u − 1` is exact in binary64; `0.2 · (·)`, `S · δ` and `x_init + S δ` are each one correctly rounded operation. The key is

    T06-ens-v1|<profile>|<case id>|<start:02d>|<joint:02d>|<coordinate id>|<attempt:02d>

with `profile = nominal` (§6.7 for the others), `start ∈ 00…19`, `joint` the start-level attempt, `coordinate id` the implementation's variable id, `attempt` the coordinate-level attempt. **(A3)** `<case id>` is the case's registered **fixture** id (§3.2's fixture column), not its corpus id — the KATs' spelling: `SYN-001-nominal` for NET-01, `SYN-001-A02-360` for NET-05, `T05b:SC-1` for THM-08; the 49 fixture ids are pairwise distinct (`corpus.fixtures_unique`, generator-checked), and no fixture or coordinate id contains `|` (A21). The draw is counter-based: order-independent, platform-independent, reproducible from the key alone, with no generator state. **RNG/version identifier: `sha256-counter-v1`.** Known-answer tests: `ref.closed_form.draw_known_answers` (ten keys; e.g. `T06-ens-v1|nominal|SYN-001-nominal|00|00|S6.n.A|00` → `k53 = 1650715324349568`, `u = 0.18326621601944737`, `δ = −0.12669351359222105`).

**(A2) The generator's binary64 arithmetic, exactly.** `k = int.from_bytes(SHA-256(key)[:8], "big") >> 11`; `u = k · 2.0**-53` (exact: `k < 2⁵³`); `w = 2.0*u − 1.0` (exact); **`δ = w / 5.0`** — one correctly rounded division, i.e. the exact `0.2·(2u − 1)` rounded once, which is what "`0.2 · (·)` … one correctly rounded operation" above means. The literal `0.2 * w` multiplies by the binary64 nearest 0.2 and is **not** the registered draw: it differs by one ulp at 35 % of keys (*measured (A2)* on 100 000 keys) and at 3 of the 10 KATs (generator-checked, `draw.kats_refuse_the_literal_0.2_product`). A coordinate is then `x = x_init + S*δ`, **two separately rounded binary64 operations** (`S*δ`, then the sum; no fused multiply–add), `S` the registered scale (3, 100, 1e5, 1e5 — each exact). Each KAT carries **`u_hex` and `delta_hex`** (bit patterns; `delta_hex` is computed by the twin as the exact rational `(2k − 2⁵³)/(5·2⁵³)` rounded once, and checked nearest by an independent test); A21 compares those. The decimal `u` and `delta` fields are 17 significant digits of the exact values, informational only: at `T06-ens-v1|nominal|SYN-001-A02-360|05|00|S3.T|00` the 17-digit `delta` rounds to a different double than `delta_hex` (generator-checked). The stress profiles (§6.7) use the same `u`: `box` is `lo + (hi − lo)*u` (three roundings, left to right); `log` evaluates `10.0 ** (4.0*u − 2.0)` with CPython's `float.__pow__` (the platform's `pow`, not correctly rounded, so not promised across platforms — the published starts file is the authority, §6.5).

### 6.4 Domain, rejection and caps

- **Per-coordinate (box) domain**: the plan's declared bounds (flows ≥ 0), intersected with the provider's declared domain for `T ∈ [280, 440]` K and `P ∈ [5e4, 2e5]` Pa. A draw outside is rejected and redrawn with `attempt + 1`. The feasible fraction of every coordinate's interval is ≥ ½ (the initializer value is inside the domain and every domain is a half-line or wider than the interval), so the cap of **64 attempts per coordinate** fails with probability ≤ 2⁻⁶⁴.
- **Start-level (joint) domain**: the start assembly must succeed — the SYN-001 traversal must admit `t` (K03 §10.1's mixer check), and on the revision path step 5 must not refuse (`kernel_refused`). A refusal redraws the whole start with `joint + 1`; **cap 64 joint attempts**. The reason of every rejection is recorded.
- **(A2) F4's recording choices, ratified.** A start assembly or restart reconstruction the kernel refuses is recorded `kernel_refused`, with the refusing unit and the kernel's status as separate fields (the restart's rejection record is `(pass index, unit, status, code)`; the starts file's joint-rejection reason is `kernel_refused` with the same fields). ADR 0015's P5, given a failed region result with **no** provenance item, reads item 0's source as `traversal-G0-v1`: every path that starts anywhere else records its source in item 0 (the ensemble's injection point writes `user_guess`), so an absent item means the registered initializer.
- **A start the generator cannot produce within the caps is `F-GEN`** (§7.2), counted in the denominator as a failure. Generation runs, and is committed, before any solve; a generation failure is therefore known before scoring, and the only permitted response is a design-lane amendment of the case's selected coordinates made and recorded before any ensemble solve — never of the profile, the scales or the caps.

## 7. Scoring, the gate and the reports

### 7.1 Success

A start **succeeds** iff (S1) the run's outcome is `CONVERGED` by any recorded path — **(A1, Frank 2026-09-26) including edge 3's sequential restart**, which discards the perturbed start and re-initializes from `traversal-G0-pass8-v1`; such a start is **rescued** (its trace has `eo_recovery: taken` and a recovery item with `initializer_source = traversal-G0-pass8-v1`) and is counted and reported separately (§7.4); (S2) its certificate is `VERIFIED` under `K04-check-policy-v1` (`check_policy_sha256` unchanged; `RELAXED` never counts, plan §6.2); (S3) the certified state is within T02 §6.4's allowances (flows 3.1e-7 mol/s, `T` 1e-5 K, `P` 0.1 Pa, duty and work 1e-2 W) of the case's registered root on every coordinate the case's reference registers; and (S4) its total wall time is at most the ceiling of §7.5.

**(A4)** S3's allowances do not change. Their argument (T02 §6.4) assumed the solver's last residual overshoots its tolerance by orders. Under `T06-revision-v1` that was not promised (K04 F3), and run 1 measured the consequence (THM-09, finding 19). Under `T06-revision-v2` the solver promises it to first order at every `k ≥ 1` exit that keeps its refinement: `|x − x*|_j ≲ τ_kind(j) = allowance/10` (ADR 0018 D2; heat rate 1/9.90).

| `F-CRASH` | an exception that is not a typed outcome escaped the solve or the verifier. **A defect**: every `F-CRASH` must be fixed before T06 is `tested` (rule 5; F3 is one) |
| `F-TIME` | S4 fails |
| `F-BUDGET` | a budget-exhaustion outcome — **(A3)** exactly an outcome K04's failure taxonomy (`verify/failure.py::TAXONOMY`) classes as `budget/cancellation outcomes`: today `BUDGET_EXHAUSTED` and `ATTEMPTS_EXHAUSTED` (the phase contract's attempt budget). `ATTEMPTS_EXHAUSTED` is also an edge-3 trigger, so on the revision path it is a start's outcome only when the restart has not rescued it |
| `F-TYPED(<outcome>)` | any other typed non-`CONVERGED` outcome, with its word (`BOUND_BLOCKED`, `STAGNATION`, `ACTIVE_SET_CYCLING`, `HOMOTOPY_STALLED`, `INITIALIZATION_FAILED`, `LINEAR_SOLVE_FAILED`, …) |
| `F-FALSE-SUCCESS-CAUGHT` | `CONVERGED` and the certificate `FAILED` (`false_success_detected`) — the verifier caught the solver |
| `F-UNVERIFIED(<reason>)` | `CONVERGED`, certificate `UNVERIFIED` |
| `F-OTHER-ROOT` | `VERIFIED` but S3 fails. **Every one is a potential false verification**: V20's "no false verification" clause fails until the design lane shows, with a twin evaluation of the case's equations at the certified state, that it is a genuine second root (then it is a finding against the case's registration, reported, and the start remains a failure) |

**(A4) The explanation route is not widened.** An `F-OTHER-ROOT` can be three things: a genuine second root, a false verification, or the registered root outside S3 but inside the certificate's own `b`. Run 1's four THM-09 starts are the third kind. The design lane's diagnosis (Amendment 4) shows they are **not false verifications**: every compiled row passes at the certified state, the twin reproduces the row, and `b` covers the distance. They are still **not explained** in this table's sense, because the only registered explanation is a genuine second root. Run 1's gate therefore stays FAIL. A future `F-OTHER-ROOT` of the third kind fails the gate term the same way: under `T06-revision-v2` it would mean a refinement was reverted or abandoned, or the chord estimate missed by more than tenfold. Either is a defect worth seeing (A90). **Rejected:** adding "the registered root within `b`" to the explanations. Written after four starts failed, it would flip run 1's gate by relabelling (R-087).

### 7.3 The gate (V20's robustness clause)

**Pass iff `S ≥ 418` of `N = 440`** — `S_min = ⌈0.95 N⌉`, the blueprint's "at least 95 % verified success", computed on the point estimate — **and there is no unexplained `F-OTHER-ROOT` and no `F-CRASH`**. It is evaluated on the reference machine class and separately on the CI aarch64 runner; V20's clause holds only if it holds on both. A rate below 0.95 is reported as a failed gate (CLAUDE.md "Scientific conduct").

**(A5) What may change after an ensemble solve has been seen (R-087).** Nothing that *scores* a start may change: `N`, `S_min`, the eligible cases, the sampling law and the published starts, S1–S4 with T02 §6.4's allowances and the registered roots, the failure classes and their conditions (§7.2's explanation route included), the budgets and the ceiling. A remedy to the *solver* or the *verifier* — a registered policy value or a corrected check — may be registered after a solve has been seen, only by a design-lane amendment that names it. The full registered gate is then re-run on both machine classes (plan §6.5: "Do not skip the full registered gate after changing a solver policy"), and every earlier run stays on record, unedited and not re-judged. Run 2 is such a re-run (Amendment 4: `T06-revision-v2`, §8.8). A re-run that only adds records to the same software (run 2r, A98) or scores a fresh draw (the holdout, §7.6 (A5)) is not a new gate result. *Pre-A5 text:* "nothing in §6 may be changed after any ensemble solve has been seen" — contradicted by Amendment 4's own §6.6 edit (the verdicts' F-1). The `verdict` agent decided run 2 under R-087 and plan §6.5; this paragraph writes that rule here.

### 7.4 Uncertainty, clustering, and what is reported

The 22 cases are a fixed, registered set; the randomness is the starts, drawn independently within each case. The estimand is `θ = (1/22) Σ_c p_c`, the mean over the registered cases of each case's success probability under the nominal law. Because every case has 20 starts, `θ̂ = S/N`, and its sampling variance `(1/(N·22)) Σ_c p_c(1 − p_c)` is at most the binomial `θ(1 − θ)/N` (by concavity of `p(1 − p)`), so **the one-sided 95 % Clopper–Pearson lower bound on `S/N` is reported as the start-sampling uncertainty for these 22 cases** (`ref.closed_form.gate.clopper_pearson_one_sided_95_lower`, `S = 410…440`; e.g. 0.929 370 at `S = 418`, 0.993 215 at `S = 440`). It does not gate (Q7): gating on it would demand `S ≥ 426` (96.8 %), a stricter gate than blueprint §13.4 registers. **No statement is made about other process designs**: 440 starts are not 440 designs (plan §6.2), and the report says so in those words. Reported per case: `p_c = s_c/20`, its failure classes, and the distinct root fingerprints among its `VERIFIED` runs (the D11 branch census; more than one is a finding). Reported across cases: how many have `p_c = 1`, `< 1`, `< 0.8`.

**(A1) Rescued starts.** Per case, `s_c = s_c^first + s_c^rescued`, where `s_c^first` counts successes whose outcome was reached from the perturbed start (no restart) and `s_c^rescued` those reached through the restart; overall `S = S^first + S^rescued`. The gate is on `S` (Frank, 2026-09-26). The report states, in these words or equivalent: *"A rescued start's outcome does not depend on its perturbation: the restart discards it, so the restart's result is the same for every rescued start of a case, and on an acyclic case the restart starts at the causal answer. `p_c^first = s_c^first/20` is the evidence about Newton's basin; `p_c` is the evidence about the solver with its registered fallbacks."* The start indicators stay independent within a case (each is a fixed function of its own draw: success iff the first solve succeeds, or it fails and the case's one restart result is a success), so §7.4's Clopper–Pearson argument is unchanged; the bound is computed on `S` and, for information, on `S^first`; neither gates. No threshold applies to `S^first`.

**(A2) The wording is fixed, not "equivalent".** ADR 0015's P5 never fires on a `user_guess` item 0, so on an acyclic case every start whose first solve ends in an edge-3 trigger is re-solved from the causal answer. The report carries, per case, `s_c/20`, **`s_c^first/20`**, `s_c^rescued` and an **`acyclic`** flag computed from the case's execution plan (no torn stream) — never typed from a list; overall `S`, `S^first`, `S^rescued` and both Clopper–Pearson bounds. It states, verbatim, the sentence quoted above, and then, with `<n>` and `<ids>` filled from the flags: *"On the <n> acyclic cases (<ids>) the restart starts at the causal answer — the registered initializer's own start — so every start of these cases that fails from its perturbation with an edge-3 trigger is rescued by a solve that does not depend on the perturbation; for these cases `p_c` says nothing about Newton's basin, and `p_c^first` says all of it."* This text's "nine acyclic cases" (§6.2, §15) is a claim the count checks: if `<n>` ≠ 9 the report says so and the difference is a finding against this text, not a reason to change the flag (A84). **(A3)** The check fired at M7: the plans count **ten** — STR-01, STA-01, STA-05, NUM-03, THM-01, THM-02, THM-07, THM-08, THM-09, THM-10 — and the text now says ten (§6.2, §15). The check stays, against 10: if `<n>` ≠ 10 the report says so, as before.

**(A4) The branch census stays as registered; NET-11's second fingerprint is a finding.** In run 1, NET-11 reported "roots 2". Start 16's certificate records `U-HEAT` `TWO_PHASE` where start 0's records `LIQUID`. The two states are 3.9e-11 apart (scaled), and start 16's heater outlet carries `S4.V = 6.3e-11 mol/s` at the pinned 370 K, where its liquid's bubble point is 373.337 K (twin `NET-11_heater_outlet_bubble_excess_K` = 3.3368 K). That label is false. The rows pass because `V·L·(y − Kx)` vanishes with `V`. The independent split passes because `|6.3e-11| < τ_flow`. The old closure passed because it is identically zero (§8.8). The census did its job, which is to surface disagreeing labels, so its clustering does not change: a fingerprint carries its labels, and merging "the same state under two labels" would hide exactly this. After §8.8 the verifier fails that certificate (`phase_admissibility.U-HEAT.S4.closure`, 3.34 K), so a start like it is `F-FALSE-SUCCESS-CAUGHT` and never a second `VERIFIED` fingerprint. Whether the solver should convert such a label itself is Q22.

**Numerical report:** per case, the distributions (median, 95th percentile, maximum) of iterations, attempts, property calls, recovery edges and fallbacks used, final `rcond₁`, `b`, start `‖F̂‖∞`. **Cost report:** per case and overall, median, 95th percentile and maximum of the four wall times, and the shifted geometric mean of total time with shift 10 ms (blueprint §13.4: the shift stated). No cross-simulator cost comparison is made (§9.6).

### 7.6 (A5) The holdout ensemble `holdout1` (Frank, 2026-09-27; reported, never gated; R-089)

**What it is for.** Run 2 re-scored the 440 draws whose run-1 failures informed ADR 0018, so its Clopper–Pearson bound is not an out-of-sample estimate for `T06-revision-v2` (the verdicts' §2.3 (b)). `holdout1` is a fresh draw from the same law, scored by the same rules and reported beside run 2. It does not gate V20, and none of its outcomes changes run 2's gate verdict. What it changes is what a release report may say (the verdicts' §2.6).

**The draw.** The nominal law of §6.2–§6.4 is unchanged: the 22 eligible cases, their selected coordinates, scales and boxes, the caps, and the start assembly. The only difference is the start index, which runs over **20…39** for every case. The key is therefore `T06-ens-v1|nominal|<fixture>|<start:02d>|<joint:02d>|<coordinate id>|<attempt:02d>` with `start ∈ 20…39`, and the per-start key prefixes are `T06-ens-v1|nominal|<fixture>|20` … `|39`.

- **These keys are never the gate's.** The gate's start field is `00…19`, and no field contains `|` (A21), so every holdout key differs from every gate key as a string. SHA-256 then makes the draws independent of the gate's.
- **Indices 20…39 are reserved to `holdout1`.** A later draw under this law takes 40 and up.
- **Why not a new first field (a new prefix).** `benchmarks/t06/generator.py` is frozen with the file it wrote: its SHA-256 is in `starts-nominal-v1.json`, and A25 regenerates that file byte for byte. Its draw loop (`draw_coordinate`) passes no prefix to `draw_key`. A new prefix would need either an edit, which breaks A25 by design, or a second implementation of the draw loop, which is a second law that would have to be proved equal to the first. `generator.generate_start(setup, index)` already takes the index, so the holdout is the frozen generator's own output at other indices, with no new drawing code.

**Generation, before any holdout solve.** `scripts/t06_ensemble.py generate --holdout` runs on `ref-x86-64` only (§7.5 (A5)). For every ensemble case, in the nominal file's case order (`ensemble_cases()`, as `_generate` iterates), it calls `generator.generate_start(ensemble.setup(case), i)` for `i = 20…39`. It then calls `generator.document(...)` exactly as the nominal `_generate` does: `policies` is each case's current registered policy id, `provider` is the live provider's block, and `machine` is the host. `generator.write` writes the result to **`benchmarks/t06/ensemble/starts-nominal-holdout1.json`**, and the command refuses to overwrite an existing file.

- **Commit.** The file is committed alone, together with the registry's `ensemble.holdout` entry (its `starts_sha256`), before any holdout start is solved. Every holdout run record's `commit` must have that commit as an ancestor (A99 (b)).
- **A start the generator cannot produce** is `F-GEN`. It is recorded in the file and counted as a failure in the holdout's 440. The holdout gets no amendment of the selected coordinates, because that would change the law.
- **A85 (a) and (b) are evaluated over the holdout file before any solve.** A start inside the degeneracy window is reported in the holdout report and scored as generated. It is never re-drawn.

**The run.** It runs at the closing commit, the same commit as run 2r (A98). `scripts/t06_ensemble.py run --run-id holdout1` runs over the holdout file on `ref-x86-64` and, in one CI dispatch, on `ci-x86-64` and `ci-aarch64`. It uses run 2's policies (`T06-revision-v2`, `SYN-001-K03`, `T04-W12`, by hash), budgets, ceiling and cache condition. The records are §6.6 (A5)'s.

**The report.** `scripts/t06_ensemble.py report` runs on each file.

- **Content.** Everything §7.4 reports:
  - per case, `s_c/20`, `s_c^first/20`, `s_c^rescued`, the acyclic flag, the classes and the root census;
  - overall, `S`, `S^first`, `S^rescued` and both Clopper–Pearson bounds;

- **Header and gate line.** It is headed `HOLDOUT holdout1 — reported, never gated (T06 spec §7.6 (A5))`. It carries **no** gate line; instead it prints `S_holdout − S_run2` for its class.
- **Across classes.** `compare` runs across the three files (A35).
- **Replay (A34).** It replays the first start (20) of every case and every retained failure.

**Where it lives, and how it enters the manifest.**

- **Starts:** `benchmarks/t06/ensemble/starts-nominal-holdout1.json` (registry `ensemble.holdout`).
- **Run files, reports and the cross-class comparison:** in `benchmarks/t06/ensemble/runs/` (§6.6 (A5), R-090), as `holdout1-<class>.json`, `holdout1-<class>.report.txt` and `holdout1.compare.txt`, each listed in that directory's `SHA256SUMS`.

**What an outcome in it means.**

## 8. The verifier's breadth ([A08], D05, D14, [A09])

### 8.1 The regularity estimator is deterministic (ADR 0014 D4)

`verify/regularity.py`'s two `onenormest` calls run with numpy's legacy global generator **saved, seeded with `20260925`, and restored** around each call, so the estimate, `rcond₁` and `b` are functions of the matrix alone and the caller's random state is unchanged. The algorithm and the recipe stay plan §6.3's (`splu` → `onenormest(t = 2)` → `rcond₁`), so no plan departure; `RegularityEvidence.method` stays `splu_onenormest_rcond1`; no schema, threshold, status or check-policy byte changes. Rejected: `t = 1` (weaker, and still an estimate); the exact `‖Ĵ⁻¹‖₁` in the certificate (departs from plan §6.3 and moves every recorded `rcond₁`); leaving it random (same-machine replay of `b` is not exact, D20).

**(A2) Deterministic is not exact.** The seed makes the estimate a function of the matrix; it does not make it the norm. *Measured (build lane, W2/W3):* at A42's constructed state (`n = 19`) seeds 0–19 each return 5.9948 (the exact `‖Ĵ⁻¹‖₁`) and `20260925` returns 4.0300 — a lower bound, ratio 0.672 — so `rcond₁` is recorded 0.0608 instead of 0.0409. Phase M's M5 finding "exact at all 258 registered matrices" is a property of those matrices, not of the seed. A38 still holds (it compares registered certificates with M5's 20-seed spread), and A42's assertion names no `rcond₁`. An underestimate errs toward `NO_RANK_LOSS_DETECTED`, so the protection is §8.3's exact-norm status check, which A2 extends from the ensemble to every certificate the corpus issues (A32). **Rejected:** choosing another seed because it is exact at a known fixture (tuning a registered constant on an observed value; it would not be exact at the next matrix).

### 8.2 The alias certificate's shifted state stays in the domain, and the verifier never raises on a converged solve (ADR 0014 D5)

`BoundDeclaration._aliases` keeps K03 §7.2's construction — every pressure column moved by a distinct amount `s_j = 997·(j + 1)` Pa, `j` its position in `variable_ids` — with one change: **a column is moved up when the provider's own domain predicate admits `P + s_j`, else down when it admits `P − s_j`, else the alias certificate is `unsupported` (reason `pressure_shift_outside_domain`)**; and if two pressures distinct at `x` coincide at the shifted state, likewise `unsupported` (reason `pressure_shift_not_generic`). Because every registered case certifies today without leaving the domain, the rule picks "up" everywhere they are concerned and their certificates are bit-identical by construction (W2's inertness proof measures it). **Any evaluation failure at a state the verifier constructs** — the shifted state, a witness stencil point, the projection of ADR 0013 D1 — is a typed result: the check it serves is `unsupported` with the reason, the verdict `UNVERIFIED`; no `VerifierError` leaves `verify` or `verify_revision` for a `CONVERGED` solve that carries its full state. (Misuse — a non-SYN-001 flowsheet handed to `verify` — may still raise; that is a programming error, not an outcome.)

**(A2) W2's choices, ratified.** Reason spellings: `pressure_shift_outside_domain`, `pressure_shift_not_generic`, `shifted_state_<status>` (`<status>` the residual's `EvaluationResult.status`), `witness_stencil_<status>(<column id>)`, `projection_unevaluable(<first line of the failing evaluation's message>)`. A reason is not in K05's R0 projection of a certificate (which carries check ids, results, near-threshold flags and limitation kinds; `run/identity.py`), so a float inside `projection_unevaluable(…)` does not break R-029; a later change that puts reasons into R0 must first remove it. When the shifted state cannot be built or evaluated, the alias rows are still **eliminated structurally** (from the Jacobian's coefficients and the mismatch at `x_final`) and every alias certificate is `unsupported` — the regularity matrix stays square and the verdict is at most `UNVERIFIED`. **With no eliminated alias row there is no alias certificate**, so an inadmissible shift changes nothing and a certificate may stay `VERIFIED`: the shifted state serves the alias certificates and nothing else (K03 §7.2).

### 8.3 Estimator accuracy is checked where it could matter

At **every certified final state of the ensemble** the harness computes the exact `‖Ĵ⁻¹‖₁` from the dense inverse (every T06 matrix has `n ≤ 128`) and records `estimate/exact`. Asserted: the estimate never exceeds the exact norm by more than 1e-12 relative (it is a lower estimate), and **the regularity status decided with the exact norm — `τ_ill`'s relative test and K04 §7.4's absolute limit — equals the recorded status** at every state. The ratio's distribution is reported. A status flip is a finding against K04 §7.2, not a tolerance to widen. **(A2)** The same check runs at **every certificate the corpus issues** (A02's 27 cases, A47's our-side REF solves, VER-01's twin, STR-05's twin, ADV-06 L/M), not only at ensemble states (§8.1 (A2)).

- Plan §6.3's two matrices are registered and stay: the triangular family TRI-16/32/64 (U-diagonal ratio exactly 1, three statuses) and `x² = 0` (SQ-0, SQ-1, SQ-2) — VER-04. T06 re-asserts them after §8.1.

  **(A4) Which checks are qualified.** The certificate qualifies a check iff the check consulted the provider (`verify/certificate.py`: an entry per check with an `independence_qualification`). Without `target_identity` the screen behaves as today. K04's evidence manifest (`K04.A23_A24_A25_A26_A34`) claimed the refusal tested; it was not (finding 13, §18). A82 registers the fix.

### 8.5 Units: conversion by `unit-conversion-v1`, and validation's dimension and component checks (ADR 0014 D6 as amended by A1)

**(A2) `unit-conversion-v2` (ADR 0016) supersedes `unit-conversion-v1`; the A1 text below stands where this paragraph does not change it.** Frank decided Q11 on 2026-09-26: specifications **and instance parameters** accept other common units by recorded conversion. The normative rule is ADR 0016; in brief:

- **Arithmetic.** `SI = RN(a·D(v) + b)`: `D(v)` the shortest decimal that rounds to the binary64 `v` (`repr`), `a`, `b` the unit's exact constants (for a mass row `a/D(M_c)`), exact arithmetic, **one** round-to-nearest-even; `+0.0` for zero; nonfinite or overflowing → refused (`value`). Replaces A1's "one binary64 operation on the binary64 operand" (rejected: two spellings of one quantity then bind to different doubles — −40 °C to 233.14999999999998 K, not 233.15; C1's 75.1 % to 0.7509999999999999, not 0.751; *measured (A2)*). STA-03's `26.85 degC → 300.0` and `0.1 kg/s → 1.0` and A56's control are unchanged; v1's KATs at −40, 12.34, 0.01 °C and synthetic 0.3 kg/s move by one ulp (ADR 0016 D2).
- **Table** (ADR 0016 D3; `ref.closed_form.unit_conversion_v2.rows`): `degC`, `degF` (temperature; and `temperature_difference` without offset); `kPa`, `MPa`, `bar`, `atm`, `psi` (absolute pressure: `state.P`, `outlet.P`, `parameters.pressure_drop`); `kW`, `MW` (`heat_rate`, `power`); `kmol/s`, `mmol/s`, `mol/h`, `kmol/h` (a one-component `molar_flow`); `kg/s`, `g/s`, `kg/h` (mass basis on a one-component flow, declared `molar_flow` or `mass_flow`); `%` on a **fraction** only (`split_fraction`, `efficiency`, `conversion.<c>`, `split.<c>`; and `mole_fraction`). Exact, case-sensitive spellings. Everything else stays refused (ADR 0016 D8), including `°C`, gauge and suffixed pressures (`barg`, `psig`, `psia`) and `%` on `nu.<c>`.
- **Steps** V0–V5 (ADR 0016 D4) replace U1–U6: V0 nonfinite → `value`; V1 = U1; V2 = U2; V3 = U3; V4 a matching row → convert and record; V5 → `unit`. New specification code `specification_value_unsupported(<id>)`; a parameter's `value` refusal is `parameter_quantity_invalid(<instance>.<name>)`.
- **Parameters are converted** by the same function inside `read_parameter` (R6), the one reader the legacy binding, `_read` and `DIM-01` share; `check_quantity` is applied to the parameter's **SI twin** (`value`, `bounds`, `nominal` converted by the same row, `unit` the SI unit). ADR 0001 D1.1's storage rule and P01's `check_quantity` are unchanged. The "Instance parameters are not converted" sentence below and its rejected alternative are superseded; T05's registered refusals are re-pointed (A73).
- **A component reference is judged before a unit** (changes W1's logged choice "kg/s on a component outside the table → `unit_unsupported`"). A specification whose `target.component` is not in the component set is refused for its component whatever its unit — legacy binding `Unbound("conflict", "component_unknown(<id>, <c>)")`, revision binding `specification_unsupported(<id>)` — and `DIM-01` does not judge it (`COMP-03` fails it, as STR-06); when `DIM-01` skipped any specification this way, its message says so — `every judged specification and parameter is in its kind's internal SI unit` (or the conversion list) followed by `; not judged for a component outside the set: <ids>` (`, `-joined, document order) — and its implicated ids stay the converted or refused ones. With the component mapped onto the provider's set (§8.6) and the molecular-weight table covering exactly that set, "outside the table" and "outside the set" are the same condition, so this only fixes which word the diagnosis uses.
- **Records** (ADR 0016 D6): `{source, input_id, value, unit, si_value, si_unit, rule, component, molar_mass}` (`input_id` a specification id or `<instance>.<name>`; `rule` ∈ `degC_to_K`, `degF_to_K`, `mass_to_molar`, `scale`); specifications in document order, then parameters by instance declaration order and parameter name in code-point order (a function of the canonical revision, not of a YAML mapping's key order — ratifies W1's "specifications before parameters" and fixes the order within an instance). `DIM-01`'s `PASS` message begins `converted by unit-conversion-v2: ` and lists every record as `<input_id> <value!r> <unit> -> <si!r> <si unit>` (with ` (M_<c> = <M!r> kg/mol)` for `mass_to_molar`); its `FAIL` lists every refusal in the same order (ratifies W1's order). `input_mapping.declared_components` is **always** recorded (ratifies W1; "empty for every registered revision" below now means: no conversion, and `declared_components` equal to the canonical order). An empty component list is refused `components_unsupported` by both bindings (ratifies W1; `validate()`'s `COMP-01` owns the diagnosis there).
- **Identity** (ADR 0016 D7): a converted revision binds to its SI twin bit for bit whenever the conversion returns the twin's double, which D2's arithmetic makes true whenever the twin's value is the decimal of the same quantity (23 registered pairs, generator-checked). A parameter pinned both on its instance and by a specification is compared on the converted values.

**(A1) Supersedes the pre-A1 text, which refused every non-SI unit.** Frank chose conversion (Q4). ADR 0001 — frozen with P01 — already prescribes it: D1.3 "Converting a `temperature` from °C adds 273.15", D1.4 "A mass-basis input is converted to component molar flows at validation time and the conversion is recorded in provenance (STA-03 tests this both ways)". The pre-A1 refusal contradicted D1.4 without saying so (finding 6, §18). What follows is exactly D1.3–D1.4, and nothing wider: a wider table would widen a frozen rule (Q11).

**The conversion.** One pure function in `process_runtime.units` (the layer whose docstring owns "unit conversion at the IR boundary"), named by the id **`unit-conversion-v1`**. Its inputs are a specification's `value`, `unit` and declared `kind`; the kind `k_req` its target requires, from the one target-path table the revision layer already has (`_PATH_KINDS`: `state.n` → `molar_flow`, `state.T`/`outlet.T` → `temperature`, `state.P`/`outlet.P` → `pressure`, `duty.Q` → `heat_rate`; `_PARAMETER_KINDS` for `parameters.<name>`), moved or imported, never copied; the target component `c`, if any; and the molecular-weight table. It applies these steps in order:

| Step | Condition | Result |
| --- | --- | --- |
| U1 | `k_req` unknown (a path neither table names) | identity iff `unit` is the SI unit of the declared `kind`; else U6's refusal (the path is refused elsewhere, as today) |
| U2 | declared `kind` ∉ `{k_req}`, extended by `mass_flow` when `k_req = molar_flow` and the target names one component | refused: `specification_kind_unsupported(<id>)` |
| U3 | `kind = k_req` and `unit` = the SI unit of `k_req` | identity; **no record** |
| U4 | `k_req = temperature`, `unit = "degC"` | **`value + 273.15`**, one binary64 addition (273.15 is the binary64 nearest); record rule `degC_to_K` |
| U5 | `k_req = molar_flow`, one component `c`, `unit = "kg/s"` (declared `kind` `molar_flow` or `mass_flow`) | **`value / M_c`**, one binary64 division, `M_c` the molecular weight of `c` in kg/mol; record rule `mass_to_molar` with `c` and `M_c` |
| U6 | otherwise | refused: `specification_unit_unsupported(<id>)` |

The unit decides how the number is read; the declared kind only has to be one the target admits. So `{kind: molar_flow, unit: kg/s}` (the STA-03 fixture) and `{kind: mass_flow, unit: kg/s}` convert identically, and `{kind: mass_flow, unit: mol/s}` is refused (U6). The result is not bounds-checked: a converted value outside the provider's domain is the downstream checks' business, exactly as for an SI value (§8.7). Each rule is one IEEE-754 operation on binary64 operands, so its result is correctly rounded and platform-independent; `ref.closed_form.unit_conversion_v1.known_answers` gives bit patterns, including operands where the binary64 sum differs from the exact decimal one (−40, 12.34, 0.01 °C) and where `v / M` differs from `v · (1/M)` (0.3 kg/s over 0.1, 0.2 and 0.04401 kg/mol), so an implementation of any other arithmetic fails them (generator-checked that such operands are present).

**(A5) An integer that has no binary64 reading is refused, typed (review S5).** ADR 0016 V0 reads `v` as "the binary64 value as read, finite (else refused, reason `value`)". ADR 0002 D3.3 says an integer whose magnitude exceeds 2⁵³ has no canonical binary64 form, and that it is refused, never rounded. So:

- **The rule.** Every number a reader reads from a specification (`value`) or from a parameter Quantity (`value`, `bounds.lower`, `bounds.upper`, `nominal`) that is a JSON integer with ~~`|n| > 2⁵³`~~ no binary64 reading is refused with reason `value`. It gets exactly the result the non-finite float of the same sign gets in the same field on the same path. *Amended (ADR 0002 Amendment 1, 2026-09-27):*
  - An integer's binary64 reading exists exactly when its digits are the canonical spelling of its nearest binary64. That is every integer with `|n| ≤ 2⁵³`, exactly one per binary64 in (2⁵³, 10²¹) (for example `592612204108959000`, read as 5.92612204108959e17), and none from 10²¹.
  - `units.read_number` reads that binary64 through `canonical.integer_binary64`.
  - A100's registered integers (`±(2⁵³ + 1)`, `±10⁴⁰⁰`) and results, (a) and (b), are unchanged.
  - The pair `2⁵³` / `2⁵³ + 1` still marks where refusal begins, but the refused set above 2⁵³ is no longer an interval: `2⁵³ + 2` is read exactly.
- **The codes.** They are the registered ones: `specification_value_unsupported(<id>)` for a specification and `parameter_quantity_invalid(<instance>.<name>)` for a parameter. That means `Unbound("unsupported", …)` from both bindings, and `DIM-01` `FAIL` with the code, so `validate()` returns `INVALID`.
- **Unchanged.** An integer with `|n| ≤ 2⁵³` is read exactly, as before.

*Measured (A5), `66861d5`:*

- ±∞ is refused typed on every reader path.
- `10⁴⁰⁰` raises `OverflowError` on all of them, because Python's `float(int)` raises instead of rounding.
- `2⁵³ + 1` raises `CanonicalizationError` on both bindings and on the legacy `validate()`, and passes `DIM-01` on a revision-built one (`DRAFT`). ADR 0002's own refusal escapes as an exception after the value has been read.
- `2⁵³` gives exactly what `2.0**53` gives, on every path.

The review's P3 saw only the first of these two failure classes. *Recommended mechanism* (the build lane's to choose): one reading function that every reader calls, returning `math.copysign(math.inf, n)` for such an integer, so that V0's existing refusal fires. No exception is caught anywhere else. A100 registers the result, not the mechanism. *Rejected:* catching `OverflowError` alone (it leaves 2⁵³ < `|n|` < 2¹⁰²⁴ − 2⁹⁷⁰ crashing); a new refusal code (the reason is V0's, and its codes exist); rounding such an integer (ADR 0002 D3.3 forbids it).

### 8.6 Component order is mapped onto the provider's (A1; Frank's Q3; ADR 0014 D9)

The binding's `components` (and the revision view's) are then the canonical tuple, and the declared list is kept as `input_mapping.declared_components` — **(A2) always, the canonical order included** (W1's choice, ratified: an absent value would not say whether the order was canonical or unrecorded). - **Where.** One pure function in the revision layer (`models/revision_flowsheet.py`), called by `_read` — so the revision binding and `verify_revision`'s own `parse_revision` see one order — and by the legacy binding before `_state_columns` and `_flowsheet_settings`. This is R-047's own rule — the label carries what selects expressions or ids, and after the mapping the declared order selects neither. Every registered revision declares the canonical order, so no registered label, key or hash moves.
- **The certificate reports nothing new** and is its unpermuted twin's byte for byte (*measured (A1)* for STA-04 against C2 under `T05b-v2`, with the order reset at document level: equal label `FSR1-7ce1dd350e70-…`, equal `variable_ids`, different `revision_sha256`, certificate SHA-256 equal, all 12 trace events equal). Results are keyed by component id; presenting them in the declared order is T07's.
- **Rejected.** Permuting at the provider boundary (an adapter reordering `n` on every request and every derivative column back): it touches every property call and cache key, puts a mapping inside the residual path, and makes the column order differ from the twin's, so STA-04 would agree within a tolerance instead of bit for bit. The declared order in `configuration_sha256`: two labels for one equation set, contrary to R-047. ### 8.8 (A4) The two-phase admissibility closure is the saturation closure (ADR 0014 D13; R-086)

**The defect.** K03 §8.2 registers a two-phase branch as admissible iff `v_i, l_i ≥ 0` and `Σ_i (y_i − x_i) ≤ 1e-10`, with `y = v/V`, `x = l/L`. K04 §4.7 implements it (`phase_admissibility.<U>.<S>.closure`, `verify/table.py`; `phase_admissibility.S3.closure`, `verify/checks.py`) as `Σ(v/V) − Σ(l/L)`, which is `1 − 1` to rounding for every `V, L > 0`. *Measured (A4):* `|value| ≤ 2.2e-16` on all 660 evaluations in the suite. The check has checked nothing since K03. Three consequences follow. A two-phase label whose phases are not at equilibrium passes it: NET-11 start 16 (§7.4 (A4)), and four of T05b B34's dew-point-fed states. An ADR 0013 D3 unresolved split, whose only admissibility evidence is "the branch's own check (the two-phase closure)", has none. And the rows cannot stand in for it: `Σ_i (v_i L − K_i l_i V) = V·L·(1 − Σ_i K_i x_i)`, so as `V·L → 0` the equilibrium rows say nothing about saturation — the division-free form's trivial roots, K02's registered note.

**The check (normative).** For a flowing lifted split judged two-phase — `V > 0` and `L > 0`, not temperature-degenerate (ADR 0012 D7 keeps precedence and its `.saturation` check is unchanged), resolved or unresolved (ADR 0013 D3) — at its `(T, P)`:

    value = max( |T − T_b(l, P)|, |T − T_d(v, P)| )      [K]

with `T_b(l, P)` the bubble temperature of the liquid product's flows and `T_d(v, P)` the dew temperature of the vapour product's flows. Both come from the verifier's own `verify/saturation.py` (`band_ends`: bisection to adjacent doubles on the classical bubble and dew functions, a fresh provider's `lnK` only — R-016's independence). When the bisection places a root off the domain — the sign of the function at the domain ends says which side — `T_b` or `T_d` is that domain end. The value is then a lower bound on the true distance, and it fails whenever that bound exceeds the tolerance. **Tolerance:** the policy's temperature tolerance `τ_T` (`tolerances["temperature"]`, 1e-6 K registered; the legacy set's `TEMPERATURE_TOLERANCE`). **Reference:** `KIND_REFERENCE["temperature"]` (100 K). The result, `near_threshold` and the independence qualification come from the existing `evaluated`. The id, the category and the check's place in the check list are unchanged. A `SaturationError` (a provider refusal or an exhausted bisection) makes the check `unsupported` with reason `closure_<status>`, and the verdict is at most `UNVERIFIED` (§8.2's rule; never a raise). The check is a `phase_admissibility` check, so ADR 0013 D1 evaluates it at the projection `x̃` when D1's preconditions hold, and at `x_final` otherwise — exactly as `.saturation` is.

**Why this form.** At an equilibrium two-phase split `y_i = K_i x_i`, so `Σ K_i x_i = Σ y_i = 1` and `Σ y_i/K_i = Σ x_i = 1`: the liquid is at its bubble point and the vapour at its dew point, and both are `T`. That is the content K03 §8.2 meant (its "Rachford–Rice closure"). Written in kelvin against `τ_T`, it is the same rule `.saturation` already applies to a degenerate split (`δ = max(|T − T_b|, |T − T_d|)` of the feed), so a two-phase split's admissibility has one meaning on every route. The tolerance stays a registered constant (ADR 0007's `exact_fields`), and `check_policy_sha256` does not move (the policy's table is by quantity kind, and `temperature` is in it). **Rejected:** (a) the sums `|Σ K x − 1|`, `|Σ y/K − 1|` against a fixed ε. Their sensitivity to `T` is `Σ x K ∂lnK/∂T`, which varies by mixture, so one ε is a different temperature accuracy per split, and no registered constant has that meaning. (b) A tolerance scaled by `V·L` or by the rows'. It would be a computed tolerance (ADR 0007), and it is implied by the rows anyway (the identity above). (c) Deleting the check. That would leave ADR 0013 D3's unresolved splits and every false two-phase label unguarded.

**Floor and margin (*measured (A4)*, scratch probe around the committed verifier).** At the sampled run-1 ensemble certificates judged at `x̃` (starts of NET-02, NET-03, NET-05, NET-07, NET-09, NET-10, NET-11, STR-01, STA-02, THM-01, THM-02, THM-03, THM-10): 0 to 1.36e-12 K (at most 24 ulps of `T`). Over the suite: 577 of 660 evaluations ≤ 9.8e-10 K. The rest are the registered F9 demonstrations at unprojected `x_final` (A02 family, DZ-3/DZ-10 at 1.01e-6 K — the liquid product 2.125e-8 past its bubble point, ADR 0013's item 2) and constructed failures (INJ-B2′'s 2e-5 K, a valve pressure rise at 23.3 K, B34's dew-point states at 9.5e-4…30.7 K — **(A5)** read: B34 (a)'s ten `FAILED` at 9.494e-4…30.70 K on `ref-x86-64`; "9.5e-4" was the minimum rounded up). So `τ_T` sits ≥ 1 000× above the floor at every judged state of a correct solve, and five orders below NET-11 start 16's 3.34 K. Twin anchors: 0 (to 1e-25) at THM-01's registered split; 3.3368 K at NET-11's registered liquid heater outlet (claims `A4.closure_vanishes_at_a_registered_equilibrium_split`, `A4.closure_catches_a_vanishing_vapour_at_NET-11s_liquid_heater_outlet`).

### 9.5 Verdict mechanics

The harness emits, per (fixture, tool), a **mechanical classification** by these rules, in order; the **`verdict` agent issues the recorded verdict** on that evidence, with reasons, and may not change a tolerance, a setting or a mapping:

1. The tool environment's fingerprint differs from `docs/reference-environments.md` §3, or the tool did not run → `NOT_COMPARABLE(access: <what>)`.
2. The tool reports non-convergence, or its own overall component balance (inlets = outlets; inlets + `ν ξ` = outlets for REF-07; fresh feed = products for REF-08) misses by more than 3.1e-8 mol/s on any component → `NOT_COMPARABLE(reference_accuracy: <value>)`. **(A1, M6)** *Converged* means: for IDAES, Ipopt's final solve terminated **"Optimal Solution Found"** — "Solved To Acceptable Level" (which Pyomo also calls optimal) stops at Ipopt's `acceptable_tol`, looser than the registered `tol`, so counting it would relax a registered input silently; for DWSIM, every object calculated with no solver error and, for REF-08, the `Recycle` converged within its iteration limit. For DWSIM's REF-07, whose `RCT_Conversion` does not expose the extent, `ξ = X_A · n_A,in / |ν_A|` with `X_A` the reactor's reported conversion of A: the A row of this check then holds by construction, and **B and C carry it** (disclosed in the record; rule 4 still compares all three outlet flows and the duty with the twin).
2b. **(A2) IDAES only — the smoothing self-check.** From the tool's own record (no result of ours and no twin value is read): `shift = max over every SmoothVLE state block of |T_eq − min(max(T, T_bub), T_dew)|`, with `T_eq` the block's `_teq[Vap,Liq]`, `T` its `temperature`, `T_bub`, `T_dew` its `temperature_bubble[Vap,Liq]`, `temperature_dew[Vap,Liq]`. If `shift > 1e-7 K` (`a_T/100`) or the record does not carry `eps_1 = eps_2 = 1e-8 K` on every such block → `NOT_COMPARABLE(semantics: smooth_vle_shift(<shift> K))`. W8's committed default-ε records (all IDAES fixtures and PC-2) classify so under this rule — REF-08 `5.0e-3 K`, REF-03 `9.8e-6 K` — are **retained in the dossier with that classification and the `DISAGREE` table they produced**, and are superseded by the re-run at the registered ε (blind: the tool scripts read neither our results nor the twin). After the re-run a `DISAGREE` is a genuine one and goes to the `verdict` agent; an Ipopt final solve that does not end "Optimal Solution Found" at the registered ε is rule 2's `NOT_COMPARABLE(reference_accuracy: <termination>)` and is reported to the design lane — ε is not changed on the build lane's initiative, per fixture or at all.
3. Our solve is not `VERIFIED` → `NOT_COMPARABLE(ours_not_verified)`, and a corpus failure.
4. Every registered quantity within §9.4 → `AGREE`; otherwise `DISAGREE`, with the full table (ours, tool, twin, tolerance, ratio).

Access and science stay separate (rules 1–2 against 4). A `DISAGREE` keeps its word when explained ("a justified explanation is not automatically numerical agreement", blueprint §13.3). **PC-1 (DWSIM) and PC-2 (DWSIM and IDAES; A1) must classify `DISAGREE`** (or `NOT_COMPARABLE(reference_accuracy)` if rule 2 fires, in which case that tool's comparisons on the same fixture are not comparable either); an `AGREE` on a positive control means the harness cannot see the effect it exists to see, and this section is wrong. ## 12. Frozen-interface verdict

**No frozen interface, schema, check category, quantity kind, tolerance, check-policy byte, `SolveEvent` outcome or event kind changes.** Item by item: the three Protocols are unchanged (the ensemble calls internal functions, as `benchmarks/t04/basin.py` does); `ProcessRevision` is used with existing fields only; `ValidationReport` gains two check entries on existing `stage` values (§8.5); `SolutionCertificate`/`RegularityEvidence` are unchanged (§8.1 changes values, §8.2 uses the existing `unsupported` result and `unsupported_check` limitation); `NoisyProvider` implements the frozen `PropertyProvider`; the registry is not in the frozen schema list. *Regenerated, not migrated* (R-015): validation-report fixtures (two added `PASS` entries), and any committed fixture that records an `rcond₁` or `b` (§8.1) — each regeneration states this section as its reason.

**(A1) Q3 and Q4 need no frozen-interface or schema change.** *Q3:* `ProcessRevision`'s `component_set.components` is an ordered list the schema never constrained to one order; the canonical order is a binding rule; `PropertyProvider` and `thermo/syn001.py` are untouched; the bindings' `input_mapping` is a field on non-frozen dataclasses. *Q4:* the `Specification` schema's `unit` is a free string; ADR 0001 D1.3–D1.4 (in the freeze) **prescribe** exactly `unit-conversion-v1`'s two conversions, so Q4 implements the frozen text rather than departing from it; the `Quantity` rule (a Quantity's unit is its kind's SI unit, `check_quantity`) is untouched because instance parameters are not converted; `DIM-01` uses the existing `dimensions` stage and `PASS`/`FAIL`. *M1:* `INITIALIZATION_FAILED` and `solve_closed` exist. **What would need one:** widening `unit-conversion-v1` beyond ADR 0001 D1.3–D1.4 (Q11), and adding molar masses to `PropertyCapabilities` (not proposed). **F4 (not this amendment's):** ADR 0015's two additive enum widenings (`solve-policy` `globalization.eo_recovery`; `solve-event` `eo_recovery_unsupported`), approved by Frank on 2026-09-26; the build lane commits ADR 0015 and the widening (WO1).

**(A2) Verdict for Amendment 2.** *Widened, by Frank's decision:* ADR 0001 D1 (a frozen semantic rule, `docs/interfaces-frozen.md` §3) — D1.1 is clarified for input documents and D1.4 generalized from the mass basis to ADR 0016's table (Q11, "Yes, in T06"). Nothing else frozen changes: no `Protocol`, schema keyword, quantity kind, `schemas/units.json` entry, tolerance, check-policy byte, `SolveEvent` value, `RegularityEvidence` field or status value (VER-02's refusal uses the existing `INCONCLUSIVE` and the free-string `inconclusive_reason`). *Moved, not frozen, and **for Frank**:* ADR 0017 moves SYN-001's implementation hash and with it every SYN-001 `model_version`, K05's structural hash `4ce030ca…` and the `t02`…`t05b` keys — a registered invariant several ADRs state ("must not move"), re-baselined by substitution with the proof of ADR 0017 D3. *Not frozen:* the revision binding's new code `specification_value_unsupported(<id>)`; `screen`'s new keyword; the IDAES tool input (a registered setting, §9.3).

## 15. What this specification does not establish

- **No empirical validation.** Every case is synthetic; every comparison is against another implementation of the same synthetic equations (§9.1). No real chemistry, no experimental data.
- **No statement about other process designs.** The 95 % is over 22 registered cases' start distributions (§7.4).
- **No uniqueness claim** for any case's root. The branch census reports what the ensemble found; the corpus has no physical multiple-steady-state flowsheet (ADV-05 is synthetic; the exothermic reactor PTC-R1 needs kinetics, v0.2).
- **No performance claim.** The ceiling is a hang guard; the cost report is within-platform.
- **No qualification of PTC.** **(A1)** The revision path's recovery is ADR 0015's restart, which discards the start: a rescued start is evidence about the solver with its fallbacks, not about Newton's basin, and on the ten acyclic cases (**(A3)**; the pre-A3 text said nine) the restart starts at the causal answer. `p_c^first` is the basin evidence (§7.4).
- **(A3) THM-08's and THM-09's `p_c^first` is not a near-root basin.** Every one of their starts opens the valve single-phase (11/9 and 12/8 `LIQUID`/`VAPOR`) against a two-phase root, because the perturbed outlet of a pure component is single-phase off `T_sat` (§6.2 (A3)). Their `p_c^first` measures the v2 contract's recovery of a PH-type split's regime from a single-phase opening (ADR 0012 D4 (a)); it says nothing about starts seeded in the root's regime, which the nominal law does not draw for these two cases.
- **(A1) Units** *(its first clause superseded by A2: the table is now ADR 0016's)*. `unit-conversion-v1` is ADR 0001 D1.3–D1.4's two conversions and nothing else: no statement about any other unit, about converting `bounds` or `tolerance` (no v0.1 reader), or about instance parameters (SI-only). The mass basis's component index is **not** discriminated by SYN-001's data (`M_A = M_B = M_C`, generator-checked): only A58's synthetic table sees it. Molecular weights are SYN-001's constant table, asserted equal to `components.yaml`; a revision's `record_source` is not read.
- **(A2) Units v2.** ADR 0016's table and nothing else; no statement about units in results or reports (SI), about `bounds`/`tolerance` conversion (no v0.1 reader), about gauge pressure (refused), or about the physical meaning of a pressure written without a qualifier (absolute). Unit invariance is a statement about decimals as written: a value that is not the decimal of the intended quantity (a truncated or computed number) binds to what it says.
- **(A2) F6.** ADR 0017 removes one failure mode of SYN-001's TP flash; it does not show the provider has no other, nor that a bracketed Rachford–Rice iteration never exhausts (none was found in the domain; ADR 0017). Until Frank approves ADR 0017, F6 stands as a limitation (ADR 0017 D5).
- **(A2) IDAES.** A comparison at the registered ε verifies IDAES's SmoothVLE in its near-sharp limit against SYN-001's sharp equations; it says nothing about IDAES at its default smoothing, which is a different (smoothed) equation set.
- **(A1) Component order.** Mapped for SYN-001's provider only (the canonical order is its `describe().components`); results are keyed by id, and nothing here presents them in a declared order (T07).
- **(A1)** §8.7 types the legacy tear path's initializer failure; it does not add a domain check at validation (a feed outside the provider's domain still validates `READY`).
- **No block-level rank localization.** The screen escalates to a whole-matrix SVD under K04's 2000 cap; at T06's sizes (`n ≤ 128`) the implicated block is the matrix.
- **The stress profiles are reported, not gated**, and `trivial-split` is T06's reading of the blueprint's "phase-boundary" profile, named for what it does.
- **The pilot's outcomes are regression facts about `f463e7d`**, not expectations: the expectations are the twin's roots.
- **(A4) No solution-accuracy promise from a certificate.** `VERIFIED` still certifies residual accuracy and discloses `b` (K04 F3). ADR 0018 makes the *solver* deliver a first-order error of `τ_kind` under `T06-revision-v2` at `k ≥ 1` exits that keep their refinement. It says nothing about a state converged at `k = 0`, a reverted or abandoned refinement, the tear path, NET-05's policy, a homotopy corrector, or a state someone else supplies.
- **(A4) Run 1 is not re-judged.** Amendment 4's diagnosis of its four `F-OTHER-ROOT`s (the registered root inside `b`, not a false verification) is a finding. It is not an explanation under §7.2, and it does not change run 1's gate.
- **(A4) §8.8 checks saturation, not the split's amounts.** The closure says each phase sits at its saturation temperature. How much of each phase there is remains the independent split's and the energy balance's job, and at an unresolved split (ADR 0013 D3) the amounts stay unchecked, as before.
- **(A4) No claim that ADR 0018 never degrades a solve.** D4 keeps the pre-refinement state whenever the refinement did not reach its target, so an attempt never returns a worse state or outcome than `newton`'s. Its extra provider calls still count against the solve's budget, which a later attempt of the same solve then lacks. Whether that ever matters is run 2's to measure. **(A5) It can degrade one:** under a property budget, a solve that `newton` finishes can end `BUDGET_EXHAUSTED(property_calls)` (A96, measured on THM-09 start 1 at caps of 365, 366, 375 and 385 calls). Separately, a refined state that the region's converged closure converts opens a different later path (ADR 0018 D4′ (ii); not observed). Run 2 on `ref-x86-64` hit neither: its three `F-BUDGET` starts are unchanged from run 1. Run 2r's per-attempt records settle both for every class (A90 (A5)).
- **(A5) The holdout is out-of-sample only for the start draw.** `holdout1`'s rate and bound are an estimate for these 22 cases' start distributions under `T06-revision-v2`, from draws that informed no solver change.
