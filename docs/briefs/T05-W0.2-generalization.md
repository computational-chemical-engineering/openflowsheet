# Brief — T05 W0.2: generalizing the SYN-001-specific flowsheet, lifted-split registry and K04 check set

**To:** `architect` (design lane). **From:** build lane, 2026-09-25. **Package:** T05, branch `wp/T05`.
**Deliverable:** a design note at `docs/design/T05-generalization.md` (sections listed at the end). No production code.

## 1. The question

What is the smallest generalization of (a) the flowsheet object and its traversal, (b) the
orchestrator's lifted-split registry and (c) the K04 check set that lets T05's revision-built
flowsheets (C1, C2, C3, C3X — spec §11) be **solved EO, verified, fingerprinted and R0-identified**
by the existing orchestrator and verifier — while every SYN-001 result stays **bit-identical**?
Which code paths generalize, which stay SYN-001-only and refuse a general flowsheet typed, and
in what order do the build-lane chunks land (each with its inertness proof)?

## 2. Why the architect

It changes the executor's data flow: `execute_plan`, `Syn001TearProblem`, `solve_region`'s split
list, `root_fingerprint`'s `branch_found`, `verify`/`verify_bound` and `run_session` are all typed on
`Syn001Flowsheet` and read its fields. A wrong seam here either moves a SYN-001 identity (a
defect by ADR 0011 D3) or forces a second pass through every T02–T04 path.

## 5. Constraints and invariants

- **ADR 0011 D3, all six items, measured against `docs/t05-measurements.md` W0.1:** `thermo/syn001.py`
  byte-identical (sha `75c9d5ba…`); every K02–T04 test passes **unchanged** (1915 at baseline);
  K05 `structural_sha256` `4ce030ca…` unchanged on the CI pair; `check_policy_sha256` `21c44e10…`
  unchanged; `syn001_lifted_splits`' two descriptors unchanged (repr sha `fc36484e…`); every
  committed fixture regenerated identically (R-015).
- SYN-001 certificates keep every check id, order and value (spec §12.1). T05 flowsheets use
  `<category>.<unit id>.<item>`, K02 units inside them included.
- No frozen interface, schema, check category, quantity kind, tolerance or `SolveEvent` outcome
  changes. **If your design needs one, stop and say so in the note's first section** — the build lane
  reports that to Frank rather than proceeding.
- Residual and Jacobian paths describe the same function; the verifier shares nothing with the
  solver (R-016): per-model checks evaluate from state + revision + provider only, never through a
  unit's row builders or evaluator.
- `UnitEvaluation` gains an additive field for shaft work, extent or internal duty (spec F6);
  `manifest_document`'s hard-coded `K02` package becomes a parameter (F3). Both must be inert for K02.

## 7. Genuinely open (decide these)

1. **The flowsheet seam.** A protocol (or base) that `Syn001Flowsheet` satisfies unchanged, and a
   revision-built general flowsheet (wiring + unit instances from `benchmarks/t05/cases/*.yaml`).
   Which members the orchestrator/verifier/session actually need; how the model-id → class mapping
   is done; the variable order a general `spec()` must produce.
2. **The solve path for T05 flowsheets.** EO over the whole flowsheet initialized by a sequential
   traversal with a dormant tear guess, or a generalized tear problem, or both. C2 and C3 have
   recycles (C3's tear carries temperature: spec §11.3 gives the tear-map Jacobian). What
   `execute_plan`/`build_plan` do with a general flowsheet, and what the tear path does (generalize
   or refuse typed as unsupported). C1 is acyclic (A17: "`CONVERGED` or the acyclic path's `ok`").
3. **Lifted-split discovery.** Per-unit declaration (e.g. a `lifted_splits()` member on the units
   that author one) vs a registry; how `syn001_lifted_splits` stays byte-identical in output;
   declaration order for `branch_found` (A26 lists it in declaration order).
4. **The per-model verifier table.** How check formulas are contributed per model (a verifier-side
   table keyed by model id, so the verifier stays independent of the unit code), how the SYN-001
   legacy set is dispatched so its ids/order/values are untouched, and how the flowsheet envelope
   checks (§12.2 last rows) and declared-phase admissibility enter.
5. **Mass mapping for PTC** (`syn001_residence_time`) under a general flowsheet, to give A27.
6. **R0 identity (A24):** where C1–C3 enter the K05 identity document without moving
   `structural_sha256` (a new top-level key, like `t02`–`t04`, is the build lane's assumption).
7. **Order and inertness.** The W1 chunks, each small enough to prove inert (A23) before the next;
   which existing tests prove it; what new test pins each seam.
