# Backend candidate environments (P02)

**Package:** P02 (matched CasADi and Pyomo/PyNumero/ASL spikes). **Authority:** plan §4.1 row P02 and its
two following paragraphs, §8.1 days 3–9; requirements D02 (language and compiled backend), D03 (sparse
solver), A05 (named backend comparator). **Recorded by:** Opus 5, 2026-09-10.

Neither backend is in `requirements.lock`. Each candidate lives in its own environment so the repository
environment stays exactly as pinned; `.venv-*/` is git-ignored. The inventory below starts the P03 work that
the plan says begins during P02; it is an inventory, not a selection.

## 1. Host

Debian 13, x86-64, Python 3.13.5, cmake 3.31.6, gcc (Debian 14.2.0-19) 14.2.0. PyPI reachable.

## 2. Reproduction

```bash
# candidate A
python3 -m venv .venv-casadi
.venv-casadi/bin/pip install numpy==2.2.4 scipy==1.15.3 casadi==3.8.0 pytest==8.3.5 pyyaml==6.0.2

# candidate B
python3 -m venv .venv-pyomo
.venv-pyomo/bin/pip install numpy==2.2.4 scipy==1.15.3 Pyomo==6.10.1 pytest==8.3.5 pyyaml==6.0.2
.venv-pyomo/bin/pip install setuptools==80.9.0 wheel==0.48.0   # required by build-extensions
.venv-pyomo/bin/pyomo build-extensions                          # compiles libpynumero_ASL.so
```

NumPy and SciPy are held at the repository's pinned versions in both environments so that any measured
difference is attributable to the backend and not to the array stack.

## 4. Installability, measured

**CasADi** installs from a manylinux wheel with no build step and imports immediately.

**PyNumero's ASL interface does not work from a plain `pip install Pyomo`.** Measured sequence:

| Step | Result |
| --- | --- |
| After `pip install Pyomo==6.10.1` | `AmplInterface.available()` → `False` |
| After `pyomo download-extensions` | still `False`; the command fetches `gjh` and `mcpp` only, and reports that AMPL GSL is no longer downloadable through it |
| `pyomo build-extensions` without setuptools in the venv | every target fails with `ModuleNotFoundError: No module named 'setuptools'` |
| `pyomo build-extensions` with setuptools installed | pynumero, aslfunctions, ampl_function_demo, cspline_external, mcpp build; **appsi fails** (`ModuleNotFoundError: No module named 'pybind11'`); ginac skipped; command exit code 1 |
| After that build | `AmplInterface.available()` → `True` |

Artifact: `~/.pyomo/lib/libpynumero_ASL.so`, 479 520 bytes, sha256
`a63bc651c1c34967f6202828a406fbb5abb7936c7ddaa7ed0ff5128fc0ecc60e`.

`build-extensions` exits nonzero even when the libraries P02 needs were built, because APPSI failed. APPSI is
not on the P02 route (which uses `PyomoNLP`, `ExternalGreyBoxModel` and `PyomoNLPWithGreyBoxBlocks`), so this
is recorded as a limitation, not as a blocker; it is not worked around, and the nonzero exit stands.

## 5. Bundled binaries in the CasADi wheel (start of the P03 inventory)

`casadi/` contains **221 shared objects totalling 234 809 336 bytes**. Among them are plugin shims for
commercial solvers — Gurobi, MOSEK, CPLEX, KNITRO, SNOPT, WORHP — and for HSL MA27. **No vendor library is
bundled**: `libgurobi*`, `libmosek*`, `libcplex*`, `libknitro*`, `libsnopt*`, `libworhp*`, `libhsl*` and

## 6. Route smoke tests (mechanism only, not the P02 harness)

Both composition mechanisms named in the plan were exercised on a throwaway three-output callback with two
declared structural zeros, to confirm the constructs exist and compose before the harness is written.

- **CasADi**: a `casadi.Callback` subclass with `get_sparsity_in/out`, `has_jacobian` and `get_jacobian`
  embedded in an `MX` graph. `ca.jacobian` applied the chain rule through the callback correctly, and the
  callback was evaluated once per residual evaluation.
- **Pyomo**: `PyomoNLP` evaluated an equality Jacobian in COO format, and an `ExternalGreyBoxModel` composed
  through `ExternalGreyBoxBlock` and `PyomoNLPWithGreyBoxBlocks` assembled a Jacobian in which the declared
  structural zeros of the callback survived.

Two ordering behaviours were observed and must be pinned by name rather than by position in the harness:

1. CasADi fills a sparse `DM` in **column-major (CCS) order, not triplet declaration order**. Values supplied
   in triplet order silently produce a permuted Jacobian.
2. `PyomoNLP` does **not** preserve constraint declaration order: for a model declaring `e1` then `e2`,
   `evaluate_jacobian_eq()` returned `e2` as row 0.

**The two routes do not assemble the same matrix.** CasADi eliminates the callback outputs, giving a Jacobian
in the original variables. The grey-box route carries the callback inputs and outputs as explicit primals with
`gb.output_constraints[...]` rows, so the same toy problem is 2×2 in CasADi and 7×7 in Pyomo. What is compared,
and how the measurement is matched when the variable counts differ, is fixed by the P02 composition
specification.

## 7. What this record does not establish

It does not select a backend (P03), does not measure performance, and does not verify any derivative of the
SYN-001 fixture. The smoke tests used a throwaway analytic callback, not SYN-001, and are not evidence for any
requirement. Everything measured here is from one host and one platform.
